- **【高】R-0162** Beaver標準事務タスク（R-0161）の再設計: 全体一覧を「実タスクのみ」に保つ
  - 2026-09-10 発注者原文（要点抜粋。全文は本要望の検討過程で参照する）:
    - 背景: 「現在はBeaver案件がYoukanへ同期されると、案件ごとに『見積』『請求』が普通のタスクとして生成されます。capacity上、見積・請求の工数まで考慮できる点は良いです。しかし実運用すると、全体一覧が『案件A 見積 請求／案件B 見積 請求／案件C 見積 請求』のようになり、今本当に関わっている仕事が見えにくくなりました。これはユーザーの求める全体一覧の役割と違います。」
    - 最重要UX原則: 「全体一覧には『たった今、人間が実際に抱えている・関わる必要があるタスク』だけを表示したい。capacity計算に必要だからという理由で、将来発生するだけの仕事を全体一覧へ表示してはいけません。裏側に多くの情報を持つことは問題ありません。しかし表示する情報量とcapacity計算に使う情報量を分離してください。」
    - 3種類の仕事量を区別: A.実タスク（今後実行が必要で現在すでに実行対象＝全体一覧に表示）／B.将来必要工数（条件成立で発生するがまだ今取り組む必要はない＝capacityには使うが全体一覧に出さない）／C.バッファ（予定外の遅延・誤差の余白。将来必要工数とは別概念。Y3で本当のbuffer機能を追加できる余地を残す）
    - 見積のライフサイクル: 問い合わせ等で見積作成が必要になった時点で実タスクとして全体一覧に表示。提出済み等で完了したら通常の完了タスクと同じ扱いで一覧から消える
    - 請求のライフサイクル（概念的な状態遷移案。現行Beaver statusとの整合は要調査）: 問い合わせ→将来工数・全体一覧非表示／見積済→将来工数・全体一覧非表示／受注済・進行中→将来発生がほぼ確定した工数としてcapacityに含む・全体一覧はまだ非表示／納品済→実行可能な実タスク・全体一覧に表示／請求済→完了・全体一覧非表示・残capacity0
    - 実装方式は指定しない。調査すべき3案: A.現行item保持し実行可能になるまで全体一覧から除外／B.将来必要工数をitem化せず専用のvirtual/planned workloadとして持ち実行時期になったら実タスク化／C.既存モデルを使った別の安全な方法。判断基準はデータ構造ではなく「capacityでは数えるが今やる必要がなければ全体一覧には出さない」という挙動そのもの
    - Y2二重計上防止（`effective_total(N) = max(baseline(N), Σchildren_effective_total)`）を絶対に壊さない。特に「請求を将来工数で30m数えている状態で、納品後に実タスク30mへ変わったら合計60mになる」という遷移バグを防止する。将来工数30m→実行可能化→実タスク30mは「置き換わる」のであり加算されない
    - capacity-checkでは「この案件を受けた場合、将来必要になる仕事量」を評価したい。問い合わせ中の既存案件をすべて受注確定扱いするか、capacity-check対象案件だけ仮に受注した場合として算入するか、受注済・進行中案件は確定負荷として算入するか等は現行のcapacityシミュレーションとの整合を調査してから仕様化する（推測で変更しない）
    - キャンセル・失注: 将来請求工数等の「条件付きで発生する予定工数」は残さない。実際に行った見積作業などは実績として存在してよいが残capacityには入れない
    - 管理入力を増やさない: 案件ごとの手入力・毎回の将来工数入力・毎回の表示切替・毎回の請求タスク作成・毎回のcapacity算入指定は要求しない。Beaver statusと標準設定から原則自動判断する。標準工数だけ設定変更可能なら十分
    - 対象範囲: 今回はこの機能（見積・請求の再設計）のみ。Y3全体には進まない
  - 前提: R-0161（`docs/requests_log.md`、仕様 `docs/SPEC/14_Beaver標準事務タスク.md`）の実装済み機能に対する実運用フィードバックに基づく再設計
  - 状態: 調査中（既存実装・Beaver status・Y2再帰モデル・capacity-checkの意味を調査してから仕様化する）
