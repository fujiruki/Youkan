# 0. 最初に読む順番

この文書は **Beaver B1（工数の正本・連携データ契約）が固まった後に読む** のが基本。

全体の推奨順序:

1. **Beaver B1**: 工数の正本・連携データ契約を確定
2. **Youkan Y1**: Beaver案件の受け口、未配置負荷、容量シミュレーション
3. **Beaver B2**: Youkanへのpushと容量判定表示
4. **Beaver B3**: 見積内訳を作業パッケージとして公開
5. **Youkan Y2**: 作業パッケージ→サブプロジェクト→実作業への段階分解
6. **Youkan Y3**: バッファ確認、仮配置、担当別シミュレーション

Beaver B1 のAPI契約がまだ無い場合、Youkan AIは契約を推測して実装しない。受け口の内部設計・テストダブルまでに留める。

# 1. 目的

Beaverに案件を登録した時点から、その案件をYoukanの「将来使う仕事量」として認識する。

情報は段階的に詳しくなる。

## 段階1: Beaver案件登録

```text
案件A
たぶん全体で 20h
```

この段階からYoukanの容量判定に20hを効かせる。

## 段階2: Beaver見積

```text
案件A 20h
├ 製作 12h
├ 取付 3h
└ その他 5h
```

総量へ加算するのではなく、粗い20hの中身が具体化したと扱う。

## 段階3: Youkanで実行計画

```text
製作 12h
├ 木取り 3h
├ 分決め 2h
├ 加工 4h
├ 仕上げ 1h
└ まだ分けていない 2h
```

必要になった部分だけ分解し、担当・日付・依存関係を設定する。

**粗い状態でも使えることを最優先する。詳細分解を利用条件にしない。**

# 2. システム責務

## Beaverが正本

- Beaver project ID / project code
- 案件名
- 得意先・現場
- 案件ステータス
- 納期
- 案件登録時概算工数
- 見積書由来の基準工数
- 見積内訳

## Youkanが正本

- Beaver案件とYoukanプロジェクトのリンク
- 実行用階層
- サブプロジェクト / タスク
- 担当者
- 依存関係
- 配置日
- 未配置負荷
- バッファ
- 容量判定
- 実行状態

## 禁止

- 案件名で同期対象を照合しない
- Youkanの案件名編集をBeaverへ書き戻さない
- Youkanで追加した子タスクをBeaver同期で消さない
- Beaver基準工数をYoukanの詳細計画で上書きしない
- 親工数と子工数を二重計上しない
- 日付未設定の仕事を容量計算から消さない

- `is_project`
- `project_id`
- `parent_id`
- サブタスク・階層
- `estimated_minutes`
- `due_date`
- `prep_date`
- `assigned_to`
- `item_dependencies`
- マルチテナント
- メンバー別・日別キャパシティ
- ガント
- 日別割当合計
- CapacityBar
- プロジェクト絞り込み

したがって、**別の案件管理機能をYoukan内へ作り直さない。既存のitems階層・キャパシティ機構へBeaver由来の仕事量を接続する。**

# 4. Y1: 最初に作るもの

Y1の目的は、詳細な自動スケジューラではない。

> 「まだ日付を決めていない仕事も含めて、この案件は納期までに入るか？」

を答えられるところまで。

## 4.1 Beaver案件とYoukanプロジェクトの一意リンク

案件名ではなく Beaver project ID で紐付ける。

推奨: 外部連携用の一意制約を持てる専用リンクテーブルを検討する。

概念例:

```text
external_project_links
- tenant_id
- source_system = beaver
- external_project_id
- youkan_project_id
- source_updated_at
- last_synced_at
- sync_state

UNIQUE(tenant_id, source_system, external_project_id)
```

Beaver由来の表示値や基準工数自体は `items.meta` 等に持たせてもよいが、**重複防止のidentityまでJSON任せにしない方が安全。**

藤田建具店という表示名をコードにハードコードせず、連携設定でtenant IDを解決する。

---

# 5. 「概算工数」は普通の子タスクにしない

Beaverから「20h」と来た時、以下のような偽タスクを毎回作る方式は避ける。

```text
案件A
└ 未分解作業 20h
```

理由:

- UIが「未分解作業」だらけになる
- 詳細化時に削除・減算管理が必要
- 普通の実行タスクと意味が違う

代わりに、Beaver由来の20hを **基準工数（baseline）** としてプロジェクトに持たせる。

概念:

```text
beaver_baseline_minutes = 1200
beaver_baseline_source = manual | estimate
beaver_source_updated_at = ...
```

「まだ分けていない5h」等は計算上の**仮想残量**として表示し、通常タスクにはしない。

---

# 6. 階層を分解しても二重計上しない計算

この連携の中核ルール。

## 6.1 基本

親に基準工数があり、子を一部だけ分解した場合:

```text
製作 基準5h
├ 木取り 1h
├ 分決め 1h
└ 仮想残量 3h
```

容量上は5h。

子が親を超えた場合:

```text
製作 基準5h
├ 木取り 2h
├ 分決め 2h
└ 仕上げ 2h
```

容量上は6h。

## 6.2 再帰ルール

概念的には各コンテナで、

```text
effective_total = max(source_baseline, child_effective_total)
virtual_residual = max(0, source_baseline - child_effective_total)
```

とする。

子が存在するからといって親の基準値を消さない。

### 表示

```text
製作
基準      5h
現在計画  6h
差       +1h
```

Beaverの5hは予測履歴として残す。

# 7. 完了済み仕事と「残り仕事量」

容量判定に必要なのは総工数ではなく残り工数。

概念:

```text
total_effective = max(baseline, decomposed_total)
completed_estimated = 完了した末端作業の目安時間合計
remaining_work = max(0, total_effective - completed_estimated)
```

初期版では実績時間ではなく目安時間ベースでよい。

将来、実績時間を使った予実管理へ拡張できる構造にしておく。

---

# 8. 配置済み負荷と未配置負荷を分ける

重要な概念。

## 配置済み

```text
8/28 木取り 3h
8/29 加工   4h
```

実際の日付に載っている。

## 未配置

```text
案件A 残り13h
納期 9/10
```

まだ日を決めていないが、仕事量として存在する。

カレンダー上の空白だけを見て「空いています」と言わない。

表示上は少なくとも、

- 予定上の空き
- 未配置仕事
- それらを踏まえた実質余力

を区別できるようにする。

---

# 9. Y1の容量判定は「仮想配置」でよい

Y1では自動的にスケジュールを書き換えない。

読み取り専用シミュレーションでよい。

## 入力

- 日ごとの利用可能キャパシティ
- 既に配置済みのタスク
- 未配置の既存案件
- 各案件の残り必要量
- 各案件の有効締切
- 候補案件の必要量・納期

## 推奨する考え方

未配置案件を締切の早い順に、将来の空き容量へ仮想的に充当する。

EDF（Earliest Deadline First）的なシミュレーションをベースにしてよい。

**シミュレーション結果は保存しない。**

## 返したい結果

概念例:

```json
{
  "feasible": false,
  "required_minutes": 1440,
  "buffer_minutes": 240,
  "reserved_minutes": 1680,
  "shortage_minutes": 180,
  "earliest_completion_date": "2026-09-12",
  "deadline": "2026-09-10",
  "saturated_through": "2026-09-05"
}
```

UIでは数値を全部見せる必要はない。

```text
9/10納期では3h不足
現在の仕事量だと9/5頃まで実質埋まっています
```

のように結論を優先する。

# 10. Beaverへ提供する容量判定API

Y1で、Beaverが呼べる読み取りAPIを用意する。

名前は仕様化時に決める。

概念:

```text
POST /integrations/beaver/capacity-check
```

候補案件が既に同期されている場合は external project ID で指定できるようにする。

同期前の仮案件を評価する用途も将来考えられるが、Y1では既同期案件を優先して単純化してよい。

Beaver側へ返すのは、Beaverが独自計算しなくて済む十分な情報とする。

# 11. Y1の終了条件

- [ ] Beaver project ID ↔ Youkan project ID が一意に紐付く
- [ ] 同じ案件を何度同期してもプロジェクトが増えない
- [ ] Beaverの基準工数を保存できる
- [ ] 基準工数を普通のタスクとして二重計上しない
- [ ] 日付未配置でも容量計算へ入る
- [ ] 配置済みと未配置を二重計上しない
- [ ] 納期まで「入る/入らない」をシミュレーションできる
- [ ] Beaverが呼べるcapacity API契約が明文化されている
- [ ] Youkan停止・Beaver停止など同期エラーを安全に扱える

この段階では以下を必須にしない。

- 見積行ごとのサブプロジェクト
- 自動仮配置の永続化
- 全社員への高度な自動割振り
- 学習型バッファ推定

Y1完了後、API契約をBeaver AIへ返す。

# 12. Y2: Beaver見積内訳をサブプロジェクトとして扱う

Beaver B3が安定した作業パッケージIDを提供した後に着手する。

例:

```text
案件A 基準20h
├ 製作 基準12h  ← Beaver由来パッケージ
│  ├ 木取り 3h  ← Youkanで追加
│  ├ 加工   4h  ← Youkanで追加
│  └ 仮想残量5h
├ 取付 基準3h
└ 仮想残量5h
```

## ownership

Beaver由来パッケージ:

- ラベル
- baseline
- source work key

はBeaver更新を反映する。

その下のYoukan実行タスク:

- タイトル
- 工数
- 担当
- 日付
- 依存関係

はYoukan所有。

Beaver同期でYoukan所有の子を削除しない。

## upstreamからパッケージが消えた場合

Youkanの分解済み作業を自動削除しない。

例:

```text
「この見積項目はBeaver側から削除されています。子作業が残っています」
```

として要判断にする。

# 13. 親/子は何階層でも分解可能

ユーザーは必要に応じて、

```text
製作 12h
└ 木取り 3h
   ├ 材料確認 0.5h
   ├ 荒取り   1h
   └ 仮想残量1.5h
```

まで掘れる。

ただし **分解しなくてもスケジュール・容量判定は成立する** こと。

詳細分解を促すメッセージを常時出さない。

# 14. Y3: バッファ

バッファは普通のタスクではなく、プロジェクトの予備容量として扱う。

```text
Beaver基準工数 20h
Youkan現在計画 22h
設定バッファ    4h
```

概念上:

```text
reserved_total = max(current_effective_total, beaver_baseline + buffer)
remaining_buffer = max(0, beaver_baseline + buffer - current_effective_total)
```

上例:

```text
基準+バッファ 24h
現在計画      22h
残バッファ     2h
確保量        24h
```

現在計画が25hになれば:

```text
残バッファ 0h
確保量     25h
```

つまり追加作業が発生した時、まずバッファを消費し、それを超えた時だけ必要容量が増える。

---

# 15. バッファの「思い出させ方」

常時ポップアップしない。

ユーザーが無視する通知を増やすと逆効果。

## 出すタイミング

### 1. Beaver案件を初めてスケジュール調整する時

バッファ未設定なら軽く確認。

```text
現在計画 20h
バッファ未設定
[なし] [2h] [4h] [入力]
```

### 2. 工数が大きく変わった時

例:

```text
計画 20h → 24h
現在バッファ 2h（使い切りました）
```

### 3. 納期に対する配置を確定・仮配置しようとする時

バッファが未確認または基準変更後に古くなっている時だけ確認。

### 4. バッファを使い切った時

```text
残バッファが0hになりました
予定を見直しますか？
```

## 出さないタイミング

- タスク名を編集するたび
- ガントを開くたび
- 同期するたび
- 子タスクを1つ追加するたび

`buffer_reviewed_at` だけでなく、基準工数・計画工数のversion/signatureを持ち「同じ状態について何度も聞かない」仕組みを検討する。

# 16. テンプレート

「見積」「打ち合わせ」「発注」「請求処理」などをテンプレート化する価値はある。

ただし案件作成時に全部自動生成しない。

Beaverステータスをトリガーに、必要な時だけ候補を出す。

例:

- 問い合わせ: 現調 / 打ち合わせ / 見積
- 受注済: 発注 / 製作 / 取付
- 納品済: 請求処理

**自動生成より「この段階で必要な定型作業を追加しますか？」を初期案とする。**

# 17. UX設計原則

この連携で特に重要。

## 17.1 粗くても使える

```text
案件A 20h
```

だけで容量判定できる。

## 17.2 詳細化は任意

必要なところだけ分解する。

## 17.3 入力を増やさない

「概算」「見積」「計画」などの確度をユーザーに選択させない。sourceから自動判定する。

## 17.4 整理作業を仕事にしない

Youkanを整えるためのタスク分解を強制しない。

## 17.5 ガントを読ませず結論を出す

ユーザー自身に空白を探させない。

例:

```text
この案件を入れると9/10納期では4h不足
9/12なら入る
```

## 17.6 通知より判断点

常設バナー・アニメーション・頻繁なポップアップではなく、工数変更・配置確定などの判断点だけで声をかける。

# 18. 同期時の変更ルール

## Beaverで案件名変更

YoukanのBeaver由来表示名を更新してよい。

## Beaverで納期変更

同期し、容量判定を再計算する。

## Beaver工数増加

仮想残量を増やし、容量を再計算。

## Beaver工数減少

Youkanの子タスクを削除しない。

例:

```text
Beaver基準 12h → 8h
Youkan分解済み 10h
```

なら現在計画10hを維持し、

```text
基準8h / 現在10h / +2h
```

とする。

## Beaverキャンセル

Youkanのプロジェクト・作業を即物理削除しない。

少なくとも、

- source cancelled
- 要確認
- アーカイブ候補

として扱う。

完了済み履歴を消さない。

---

# 19. 将来の「仮置き」

Y1のread-onlyシミュレーションが信頼できるようになってから、

```text
この案で仮置き
```

を追加する。

その時に初めて、1つの作業を複数日に分割予約する専用データモデルを検討する。

例:

```text
work_allocations
- item_id
- date
- minutes
- assigned_to
- state: tentative | fixed
```

既存 `estimated_minutes` や `due_date` に無理やり複数日分割を押し込まない。


# 21. 最終目的

この機能を、

> Beaver案件をYoukanへコピーする機能

として設計しない。

目的は、

> **Beaverで発生した仕事を、情報が粗い段階から仕事量として認識し、詳細化するほど精度を上げながら、Youkanが常に「この仕事は入るか」「実質いつ頃まで埋まっているか」「どれだけ余裕を残すか」を判断できるようにすること。**

である。
