# 全体一覧ドラッグでプロジェクト移動 — 機能要件

作成日: 2026-08-28  
対象: Youkan  
状態: **実装前の機能要件。SdDDで正式R-IDを発行し、既存仕様との整合を確認してから実装すること。**

---

# 1. 背景

Beaver連携Y2完了後、Youkanには以下の2種類の案件が同時に存在するケースがある。

1. 過去にYoukanへ手動登録したプロジェクトと、その配下タスク
2. Beaverから自動同期された同一案件のプロジェクトと、その配下のwork_package

今後はBeaver自動同期プロジェクトを案件の正規コンテナとして使いたいが、既存の手動タスクを1件ずつ編集画面で所属変更するのは操作負担が大きい。

専用の「案件統合画面」を増やすより、日常的に使う全体一覧画面で、ドラッグ＆ドロップによって直感的に所属先プロジェクトを変更できる方が自然である。

この機能はBeaver移行専用ではなく、通常のYoukan運用でも「このタスクを別プロジェクトへ移したい」「この作業をサブプロジェクト配下へ整理したい」という一般的な操作として利用できるものとする。

---

# 2. 目的

全体一覧画面上で、タスク／アイテムをドラッグし、任意のプロジェクトまたは入れ子のサブプロジェクトへドロップするだけで、そのアイテムの所属階層を変更できるようにする。

利用者は編集モーダルを開かず、一覧を見ながら視覚的に仕事の構造を組み替えられる。

基本操作:

```text
タスクを掴む
  ↓
移動先プロジェクトの上へドラッグ
  ↓
そのプロジェクト全体が明確にハイライト
  ↓
「○○へ移動」など、ドロップ先が明確になる
  ↓
ドロップ
  ↓
そのプロジェクト配下へ所属変更
```

---

# 3. 最重要UX要件

## 3.1 ドロップ先を迷わせない

ドラッグ中、ポインタがドロップ可能なプロジェクト領域へ入った場合、そのプロジェクトのカード／行／表示領域全体を明確にハイライトする。

単なる薄いhover表現ではなく、「今ここへドロップするとこのプロジェクトへ入る」と即座に理解できる状態にする。

推奨例:

- 背景全体を強調
- 枠線を強調
- 軽い発光または明確なコントラスト変化
- 「○○へ移動」の短い補助表示

ただし、過度なアニメーションや常時点滅は避ける。

## 3.2 入れ子プロジェクトを正確に区別する

全体一覧には既にプロジェクト／サブプロジェクトの入れ子表現がある。

その既存表示をそのままドロップ先として利用し、親プロジェクトと子プロジェクトを別々のターゲットとして扱う。

例:

```text
○○様邸
├ 製作
│ ├ 木取り
│ └ 加工
└ 取付
```

ドラッグ中:

- `○○様邸` 上 → 案件直下へ移動
- `製作` 上 → 製作配下へ移動
- `取付` 上 → 取付配下へ移動

親と子を同時にハイライトしない。現在の実ドロップ先だけが明確に強調されること。

## 3.3 ドロップ直後に結果が見える

ドロップ成功後は、一覧上でアイテムが新しい所属位置へ移動し、成功が即座に視覚確認できること。

可能なら短時間のUndoを提供する。

例:

```text
「木取り」を「製作」へ移動しました  [元に戻す]
```

Undoは必須ではないが、誤操作防止として優先度は高い。

# 4. データ・階層ルール

Y2（`docs/SPEC/08_Beaver連携Y2.md`）で確定した階層解釈を必ず継承する。

特に、Y2本番検証で `parent_id` と `project_id` の解釈による二重計上バグが発生しているため、このドラッグ操作だけ独自の階層ロジックを実装してはならない。

**既存の階層計算・親子解決ロジックを共通利用すること。**

## 4.1 ルート案件へドロップ

ルートプロジェクトへタスクをドロップした場合、そのタスクはその案件直下になる。

概念:

```text
project_id = 移動先ルート案件ID
parent_id  = 既存仕様に従い案件直下を表す値
```

`parent_id`をNULLにするか案件IDにするか等を新規に推測せず、現行Youkanの正規ルールを調査して合わせること。

## 4.2 サブプロジェクトへドロップ

入れ子プロジェクト／work_package／サブプロジェクトへドロップした場合、そのノードの子として所属させる。

概念:

```text
project_id = その階層が属するルート案件ID
parent_id  = ドロップ先サブプロジェクトID
```

ただし実際の値はY2で確定した `children(N)` 解決規則と既存更新APIに合わせる。

## 4.3 保持する情報

所属変更によって、以下を失わないこと。

- title
- status
- due_date
- prep_date
- estimated_minutes
- assigned_to
- dependencies
- meta
- 作成者情報
- その他、プロジェクト所属と無関係なユーザー編集情報

移動操作の目的は所属階層の変更のみであり、タスク内容の初期化ではない。

---

# 5. Beaver連携案件との関係

Beaver由来プロジェクト／work_packageも通常のドロップ先として扱えること。

例:

```text
Beaver自動案件: ○○様邸
├ 製作 8h      ← work_package
└ 取付 2h      ← work_package
```

既存の手動タスク:

```text
木取り 2h
加工   3h
```

これらを `製作` work_packageへドラッグすると、

```text
○○様邸
├ 製作 8h
│ ├ 木取り 2h
│ └ 加工 3h
└ 取付 2h
```

となる。

Y2の再帰負荷モデルにより、この詳細化は原則として二重計上されないこと。

ドロップ操作の実装によって、Beaver由来baselineやexternalリンク情報を書き換えないこと。

---

# 6. ドラッグ可能／ドロップ可能対象

仕様化時に現行UIを調査して最終決定するが、基本方針は以下。

## ドラッグ可能

- 通常タスク
- 必要であれば手動サブプロジェクト

## ドロップ可能

- 通常プロジェクト
- サブプロジェクト
- Beaver由来work_package

## 原則ドロップ不可

- 自分自身
- 自分の子孫ノード（循環階層になる移動）
- 削除済み／アーカイブ済み等、現行仕様で編集対象外のプロジェクト
- テナントをまたぐプロジェクト

循環参照を必ず防止する。

---

# 7. プロジェクト自体をドラッグする場合

初期版では「通常タスクの所属変更」を優先してよい。

プロジェクト／サブプロジェクト自体のドラッグ移動を同時に実装すると、循環チェック・子孫一括所属変更・Beaver外部リンクとの関係が複雑になる可能性がある。

現行実装を調査した結果、安全かつ既存ロジックを流用できるなら対応してよいが、無理に初版へ含めない。

最小実装の優先順位:

1. タスク → ルートプロジェクト
2. タスク → サブプロジェクト／work_package
3. Undo
4. プロジェクト／サブプロジェクト自体の移動

---

# 8. 名前照合禁止

この機能は「同じ名前の案件を自動で統合する機能」ではない。

Beaver連携の原則と同様、案件名を使って自動的に移動先を判断しない。

ユーザー自身がドラッグ操作で明示的に移動先を選ぶ。

これにより、同名案件・似た案件の誤統合を防ぐ。

---

# 9. 保存方法

既存のitem更新API／serviceを優先して利用する。

ドラッグ専用にDBを直接更新する独自経路を作らない。

所属変更に必要なフィールドのみ更新し、既存の認証・テナント境界・バリデーション・更新時副作用を通す。

必要であれば専用APIを追加してもよいが、その場合も既存updateロジックを内部で共通利用すること。

---

# 10. capacity / Y2負荷モデルとの整合

移動前後で、同じタスクが二重計上されたり負荷から消えたりしないこと。

特に以下をテストする。

- ルート案件Aからルート案件Bへ移動
- ルート案件直下 → work_package配下
- work_package A → work_package B
- baseline > 子タスク合計
- baseline < 子タスク合計
- 配置済みタスク
- 未配置タスク
- 完了済みタスク

Y2の `effective_total = max(baseline, Σchildren)` の再帰規則を壊さないこと。

---

# 11. UI詳細候補

実装前に既存の全体一覧コンポーネントを調査し、既存デザインへ合わせる。

推奨挙動:

### 通常時

UI面積を増やさない。常設の「移動ボタン」は不要。

### ドラッグ開始

- 掴んでいるアイテムを視覚的に浮かせる
- ドロップ可能なプロジェクトを必要なら軽く識別可能にする

### 有効なドロップ先へhover

- そのプロジェクトノードだけ明確にハイライト
- `○○へ移動` のような短いラベル

### 無効なドロップ先

- ハイライトしない
- 必要なら禁止カーソル

### ドロップ後

- 即時UI更新
- 保存失敗時は元の位置へ戻す
- エラー通知
- 可能ならUndo

---

# 12. モバイル／タッチ操作

YoukanがPWAとしてタッチ端末でも使われるため、デスクトップのHTML5 dragだけで完結させると将来利用しづらくなる可能性がある。

初版をデスクトップ優先にすることは許容するが、利用するDnDライブラリ／実装方式はタッチ対応可能なものを優先して検討する。

長押しドラッグ等を初版へ含めるかは、既存全体一覧の操作との衝突を確認して決める。

---

# 13. アクセシビリティ／代替操作

ドラッグ＆ドロップだけしか移動方法が存在しない状態は避ける。

既存編集画面でプロジェクト所属を変更できる場合はそれを代替手段として残す。

将来的にはキーボード操作や「移動先を選ぶ」メニューも検討できるが、この機能の初版では必須としない。

---

# 14. 競合・失敗時

ドラッグ中に対象アイテムまたはプロジェクトが別操作で更新された場合でも、保存失敗時に表示だけ移動済みになる状態を避ける。

基本:

1. UI上で仮移動
2. API保存
3. 成功 → 確定
4. 失敗 → 元へロールバック＋エラー表示

または保存成功後にUI移動でもよい。既存Youkanの更新体験に合わせる。

---

# 15. テスト要件

最低限以下をTDDで確認する。

## 階層

- タスクを別ルートプロジェクトへ移動
- タスクをサブプロジェクトへ移動
- タスクをBeaver work_packageへ移動
- サブプロジェクトが複数階層ある場合、正しいノードだけがターゲットになる

## データ保持

- 工数保持

- status保持

- meta保持

## 安全性

- 自分自身へのdrop禁止
- 子孫へのdropによる循環禁止（プロジェクト移動を実装する場合）
- tenant跨ぎ禁止
- archived/deleted target禁止
- API失敗時ロールバック

## Beaver/Y2

- Beaver案件直下への移動
- work_package配下への移動
- external_project_links / external_work_package_linksを壊さない
- baselineを書き換えない
- capacity計算で二重計上しない
- 移動前後で総負荷が意味なく増減しない

## UI

- hover targetだけハイライト
- nested targetを正しく識別
- ドロップ後に正しい位置へ表示

# 16. 本番受け入れ確認

実装後、最低限以下を実機確認する。

1. 手動プロジェクト内の既存タスク1件を、Beaver自動案件へドラッグ移動
2. 同じ案件内のwork_packageへ別タスクをドラッグ移動

# 17. スコープ外

初版では以下を必須にしない。

- 名前による重複案件自動検出
- 自動案件統合
- 旧プロジェクトの自動削除／自動アーカイブ
- 複数タスクの一括選択ドラッグ
- プロジェクト間の自動工数調整
- Beaverへの逆同期
- Y3（バッファ・担当別シミュレーション・自動仮配置）

---

# 18. 実装優先度の考え方

この機能の価値は、機能数ではなく「一覧を見ながら、その場で仕事の所属を直せる」ことにある。

初版は以下が成立すれば十分。

```text
掴む → 正しいプロジェクトが光る → 離す → そこへ入る
```

専用モーダル・設定画面・複雑な一括統合機能を先に作らない。

全体一覧を「見るだけの画面」ではなく、仕事の構造を直接整理できる画面へ少し拡張する、という位置づけにする。

---

# 19. Y3との関係

Y3は現在、Y2完了状態を実運用してから必要性・優先度を再判断するため保留する。

このドラッグ移動機能はY3ではなく、Y2完了後の実運用を円滑にする独立機能として扱う。

Y3の候補（別途詳細文書化予定）:

- プロジェクトバッファ
- 担当者別capacity simulation
- 仮配置
- 自動スケジューリング／配置提案

この機能の実装を理由にY3へ自動的に進まないこと。
