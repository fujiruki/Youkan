# AI専門家会議: Youkan「予実管理」の設計（2026-08-19）

## 会議の定義

- **テーマ**: 依存関係でつながる工程の「予定 vs 実際」を Youkan がどう表現し、遅れが後工程・バッファにどう波及するかを見せ、「今日はどこまでやらないといけないか」を計画しやすくするか
- **ゴール**: 意思決定（v1 の範囲と段階の切り出し。R番号分割案まで）
- **発注者原文**: 「わたしができたらいいなとおもうのは予実管理です。予定がどのくらいだったのが、どのくらい遅れてるのかというのを見て、じゃあ今日はこのくらいがんばらなくちゃ、ここまでやらないと、どの時点に入れたバッファのノードを消費するか、などという計画をしやすくしたい」
- **きっかけ**: 板２上下加工（納期 8/18、依存 板１→板２→次工程）が 8/19 にずれ込む。後工程がどうずれるかを見たい
- **前提（守るべきルール）**: 判断疲れを減らす／褒め・評価語禁止／判断は3択以下／新画面・新入力ゼロ志向／意志依存の設計は失敗する（`SYSTEM_PHILOSOPHY_AND_VISION.md`）。既存資産: `item_dependencies`（本番280本）、`estimated_minutes`、`due_date`/`prep_date`、`completed_at`、フロー日付帯（合計・最短・残り）、ガント時間軸、R-128 週負荷1行、R-129 最遅着手日トークン、R-136 超過分パネル、日次キャパ
- **裏取りした事実（本番DB 2026-08-19 スナップショット）**: バッファ／予備と題したアイテム **0件**（バッファノード運用はまだ無い）／目安時間が入っている未削除タスク **45%**（305/673）／done のうち `completed_at` あり 68%（283/417）／ベースライン・実績時間・バッファ区別のカラムは無い
- **判断基準**: 発注者が「明日から使い始められる」こと ＞ 網羅性。入力を増やさない。既存の R-129 型（計算値・1語・保存しない）に乗ること

## ラウンド1（Divergence）

### 工程実務家
**立場**: 「予定の凍結」より先に「今どれだけ遅れているか」が毎朝1行で見えれば9割足りる。
- 提案①: フローの日付帯（既にある「合計・最短・残り」）に **「見込 M/d（+N）」** を足す。前工程が今日終わると仮定した後工程の押し出しを帯単位で出す。ノード単位ではなく帯単位で十分（現場は日単位で動く）
- 提案②（意外性）: バッファは**新しいノードを置かせない**。工程の間の「空き日」がバッファ。フローの日付帯と帯の間に「空き 2日」を灰字で出せば、それがバッファの残り。ノードを増やす作業は現場では続かない
- 根拠（事実）: 本番にバッファノード0件。（意見）：置くつもりでも忙しくなると置かない
- 前提: 目安時間より「日付」の方が現場は信頼している
- 懸念: 目安時間が45%しか入っていないので、時間ベースの「今日Xh」は半分のタスクで空振りする

### 実装・保守
**立場**: ベースラインの凍結は v1 に入れない。計算値だけで始め、保存するのは1カラムまで。
- 提案①: R-129 `getLatestStart` と同じ場所に `getPushedDate(item, deps, today)`（前工程の有効締切 or 今日 の遅い方 ＋ 自分の所要日数）を純関数で1本。表示は R-129 の4箇所に同じトークン `→ 8/20 (+1)`。DB 変更ゼロ、PHP 二重実装なし（digest には出さない）
- 提案②（意外性）: 予定の凍結は「凍結ボタン」ではなく **`due_date` の変更履歴**で代替する。`items.meta.due_history: [{at, from, to}]` を PATCH 時に自動追記（保存側1箇所）。「元の予定 8/18 → 今 8/19」は履歴の先頭と現在値で出せる。ユーザーの入力ゼロ
- 根拠（事実）: `meta` はスキーマ変更なしで拡張できる（R-136 `contacted_at` の前例）。（意見）: 明示的な `planned_due` カラムは「いつ凍結するか」の運用ルールを要求し、ルールは守られない
- 懸念: 依存が枝分かれ・合流するグラフでの押し出し計算は最長経路（既存フロー帯の「最短」計算が使える）

### UX・思想番人
**立場**: 予実管理の「実」を入力させた瞬間に失敗する。実績時間は取らない。
- 提案①: 「遅れ」を数字で見せるのは超過分パネル（R-136）で既にやっている。足りないのは**「遅れが誰に波及するか」**。ノードではなく案件（得意先）単位で「板２が1日遅れると、○○様納品が 8/22→8/23」と1行。判断は「連絡する／納期を動かす／何もしない」の3択（R-136 の「連絡した」と同じ導線）
- 提案②（意外性）: 「今日はここまで」は**計算で出さず、朝に本人が1回タップで決める**（今日の focus 合計時間 vs 日次キャパ、既に R-128 週負荷で見えている）。システムが「今日Xh必要」と言い始めると評価語に近づく（「足りない」は事実だが「がんばらなくちゃ」はシステムが言うことではない）
- 前提: 発注者は「がんばらなくちゃ」を自分で言いたい。システムは事実だけ
- 懸念: バッファ残量の表示は「消費している」自責を生みうる。数字だけ、赤字なし

### 予実管理の理論家（PM/TOC）
**立場**: やろうとしているのは CCPM のバッファ管理そのもの。理論は借りるが、フィーバーチャートは作らない。
- 提案①: CCPM 流に「バッファは鎖の末端（納期の手前）に1つ」。工程ごとにバッファノードを置かせるのは理論的にも間違い（局所安全余裕が全部消費される＝学生症候群）。よって `is_buffer` フラグは**プロジェクトに1つ**（`project.meta.buffer_days`）で足りる。消費率＝（納期 − 見込完了日）÷ buffer_days
- 提案②（意外性）: バッファ消費率と鎖の進捗率の2軸（フィーバーチャート）を「色」に落とすと評価語になる。代わりに **数字1つ「バッファ 残 2/5日」** をプロジェクト行と超過分パネルの見出しに出す。緑黄赤は使わない
- 根拠（事実）: CCPM のプロジェクトバッファは鎖末端の1個が定石。（意見）: 工程間バッファはこの規模（一人親方の木工所）では管理コストが勝つ
- 懸念: 見込完了日の算出には目安時間か所要日数が要る。目安が無いタスクは「1日」と仮定するルールが必要

### 悪魔の代弁者
**立場**: 全部やらなくていい。板２の件は「納期を19日に直せば済む」話で、システムは何も足すべきでない。
- 反論①: 「予実管理」は発注者の言葉だが、本当に欲しいのは「今日サボっていいか、いけないかの判定」。それは R-128（今週 必要/枠/不足）と R-129（着手 M/d）で既に出ている。使い込まれてから足すべき
- 反論②: 押し出しトークンは「前工程が今日終わる」仮定に依存する。終わらなければ毎日ずれる数字を見せることになり、「数字が信用できない」で見られなくなる（R-128 の 433h/65h と同じ運命）
- 提案（意外性）: 何も作らず、**フロー画面で板２の納期を右クリック→「後続もずらす」だけ**（指揮AI案B）を作る。表示は増やさない。押し出しは本人が明示操作したときだけ起こす

## ラウンド2（Debate）

### 工程実務家 → 理論家の案をスチールマン
「バッファは鎖末端に1つ、`project.meta.buffer_days`、消費率は数字1つ」——これは入力が案件あたり1回で済み、フローにノードを足さなくてよい。現場向きだ。
- 反論①: ただし建具は「木取り→加工→組立→塗装→取付」で塗装の乾燥待ちのような**外部要因の待ち**が鎖の途中にある。末端バッファ1つだと「乾燥に3日見ていたが5日かかった」が可視化されない。→ 中間は `waiting` 状態の期間で見えるので、バッファは末端1つでよいが「待ちの実績」は `waiting` の滞在日数で別に拾うべき
- 反論②: 実装・保守の `due_history` 案は良いが、現場は「予定」を `due_date` ではなく**フローの日付帯（＝ prep_date）**で組む。凍結すべきは prep_date の初期値。`due_date` は得意先との約束で滅多に変わらない
- 自説修正: 帯単位の「見込」表示は維持。ノード単位トークンは詳細モーダルだけでよい

### 実装・保守 → 工程実務家の案をスチールマン
「新しいノードを置かせず、帯と帯の空き日をバッファとみなす」——入力ゼロで既存の帯計算に足すだけ。最も安い。
- 反論①: 空き日は「休日」「他案件」「単に未計画」と区別がつかない。「空き 2日」を残バッファとして見せると誤読する。理論家の末端1個 `buffer_days` の方が意味が定まる（案件あたり1入力は許容範囲）
- 反論②: 悪魔の代弁者の「毎日ずれる数字は信用されない」は正しい。だから見込は**「前工程が今日終わる」ではなく「前工程の有効締切」**を起点にすべき。締切が過ぎたら（超過分）その時点で `+N` が確定して動かない。今日起点は動的すぎる
- 自説修正: `due_history` ではなく `prep_history`（初回設定値だけを `meta.planned_prep` に1回保存、以後不変）に変更。フロー日付整列で prep が付いた瞬間が「計画」。凍結ボタン不要

### UX・思想番人 → 実装・保守の案をスチールマン
「計算値のみ、保存は初回 prep の1値、表示は R-129 の場所」——入力ゼロ・新画面ゼロで思想に完全に沿う。
- 反論①: それでも「→ 8/20 (+1)」トークンが全体一覧に何十個も並ぶと R-129 の飽和ガードと同じ問題。押し出しトークンは**依存の直後1件だけ**（鎖の全部ではなく、次の工程だけ）に出す。鎖全体の影響は案件行（プロジェクト）に集約する
- 反論②: 「今日Xh」を出さないと発注者の「今日はこのくらいがんばらなくちゃ」に応えられない、という反論があるだろう。だが R-128 の週負荷1行が既にそれ。足すなら「今日」版の1行（今日 必要Yh／枠Xh）だけで、バッファと結びつけない
- 自説修正: 「本人が朝タップで決める」は撤回。既存の週負荷1行に「今日」版を足すだけなら意志依存ではない

### 理論家 → UX・思想番人の案をスチールマン
「波及は案件（得意先）単位で1行、判断は連絡／納期変更／何もしない」——R-136 の導線に自然に乗る。
- 反論①: 案件単位に丸めると「どの工程がボトルネックか」が消える。CCPM の肝は制約工程の特定。少なくとも案件行の1行に「原因: 板２（+1）」を添えないと、連絡はできても手は打てない
- 反論②: 「実績時間は取らない」は賛成だが、**`completed_at` は既にある**。予定 prep と completed_at の差（日単位）は入力ゼロで「実」になる。これを捨てる理由はない。案件ごとの「平均 +0.8日」は次の計画の目安倍率になる（R-129 の安全係数1.5を実測で置き換える道）
- 自説修正: バッファ末端1個は維持。ただし v1 では `buffer_days` も入れず「納期 − 見込完了日 ＝ 余裕 N日」を出すだけでよい。余裕がマイナスになった時が「バッファ切れ」

### 悪魔の代弁者
形成されつつある合意（計算値トークン＋初回 prep 保存＋案件行の余裕日数）を崩す:
- 目安時間 45%・prep_date もフローで整列した案件しか付いていない。**入力が揃っている案件は少数**で、揃っていない案件は「見込 —」ばかりになる。作っても大半の案件で空欄なら「使えない機能」と認識される。先に「石鎚山」1案件で紙（スプレッドシート）でやって、要る数字を確かめるべき
- 「余裕 N日」は納期側から引く。しかし発注者の実態は R-136 で見た通り**94件が超過中**で、余裕は大半がマイナス。マイナスの山を見せることになる。R-129 と同様「期限が先の案件だけ」に限定しないと赤の飽和の再演
- 反対を残す: 押し出しの自動計算は「前工程の締切」起点でも「本人がその締切を守る」仮定に立つ。守られていない案件では見込は嘘になる

## ラウンド3（Convergence）

### 論点整理
| 論点 | 採用 | 棄却 |
|:--|:--|:--|
| ベースラインの凍結 | **初回 prep_date を `meta.planned_prep` に自動保存**（凍結ボタンなし、以後不変。due は得意先との約束なので凍結不要） | 明示的な凍結操作／`planned_due` カラム／`due_history` |
| 実績 | **`completed_at` − `planned_prep` の日数差**（入力ゼロ） | 実績時間の入力 |
| 押し出し（見込） | **前工程の有効締切（超過分は超過中の締切そのもの）を起点**にした純関数、直後の1工程だけにトークン。鎖全体は案件行に集約 | 今日起点の動的計算／鎖全ノードへのトークン |
| バッファ | **v1 はバッファ入力なし**。案件行に「余裕 N日」（納期 − 見込完了）を数字だけ。期限が先の案件に限定（R-129 と同じ飽和回避） | 工程ごとのバッファノード／`is_buffer` フラグ／フィーバーチャート色分け／帯間の空き日＝バッファ |
| 「今日はここまで」 | **R-128 週負荷1行の「今日」版**（今日 必要Yh／枠Xh）。バッファとは結びつけない | 「次のバッファを守るには今日Xh」の逆算 |
| 締切変更時の連鎖 | **指揮AI案B（後続もずらす／この1件だけ／戻す）を v1 に含める**（悪魔の代弁者の唯一の賛成点。明示操作なら思想に反しない） | 自動書き換え |
| 表示の主戦場 | フロー日付帯（見込 M/d）＋案件行（余裕 N日・原因工程）＋詳細モーダル（→ M/d (+N)、planned→現在） | 全体一覧への全ノード表示 |

### トレードオフ
- 入力ゼロを守る代わりに、prep_date が付いていない案件では何も出ない（本番の45%問題）。「出ない」を許容し、フロー日付整列を使っている案件から効き始める設計にする
- 「余裕 N日」は期限が先の案件に限定するため、既に超過している案件（大半）には効かない。それらは R-136 超過分パネルの領分と割り切る

### 簡易プレモーテム
採用案が6ヶ月後に失敗していたとしたら——原因は「見込が信用されなくなった」こと。前工程の締切起点でも、その締切自体が守られない案件では見込は嘘のまま固定され、発注者は「またずれてる」ではなく「この数字は当てにならない」と学習して見なくなる。二番目の原因は「prep_date を付ける習慣が付かず、ほとんどの案件で空欄」。対策は (1) 見込は「締切起点」と明記して「予定通りなら」の数字だと表示上も伝える（`予定通りなら 8/20`）(2) 効いている案件数を数え、3ヶ月で増えていなければ prep_date 自動付与（フロー日付整列時の保存）を検討する

## 最終結論

- **結論: 条件付き Yes**。「予実管理」を独立機能として作らず、既存の R-129/R-136/R-128 の場所に **入力ゼロの計算値**として3段階で足す。条件: 実績時間の入力・バッファノード・凍結操作・色分けは作らない
- **採用理由**: 発注者の目的（遅れの把握→今日の計画→バッファ消費の見通し）は「見込日」「余裕日数」「今日版の負荷1行」の3つの数字で満たせ、いずれも既存カラムと1つの meta 値だけで出せる。思想（入力ゼロ・評価語なし・3択）に反しない
- **棄却案と理由**: 工程ごとのバッファノード（本番0件、続かない、CCPM でも誤り）／フィーバーチャート色分け（評価語化）／実績時間入力（意志依存）／今日起点の押し出し（毎日動いて信用を失う）／帯間の空き日＝バッファ（休日・未計画と区別不能）
- **想定リスクと対策**: 見込の不信 → 「予定通りなら M/d」の文言で仮定を露出。prep 未入力で空欄 → 効いている案件数を追い、増えなければ自動付与へ。マイナス余裕の飽和 → 期限が先の案件に限定
- **少数意見（残す）**: (a) 悪魔の代弁者「まず石鎚山1案件でスプレッドシートで数字を確かめてから作れ」——v1 を最小にしたので着手はするが、v1 リリース後1ヶ月は数字の当たり外れを発注者に聞く。(b) 理論家「末端バッファ `buffer_days` の明示入力」——余裕 N日で不足を感じたら v3 で1入力だけ足す。(c) 工程実務家「`waiting` 滞在日数で待ち工程の実績を拾う」——塗装乾燥など外部待ちの見積り改善に効く。別要望として保留
- **確信度: 中**。上げるために次に確かめること: 発注者の実運用で「予定」は prep_date（フロー日付整列）で組んでいるか、それとも due_date か（凍結対象の前提）。石鎚山案件で prep_date が付いている工程の割合
- **次アクション（R番号分割案）**:
  1. **v1（1本目）**: 押し出し見込トークン（前工程の有効締切起点、直後1工程のみ、`予定通りなら M/d (+N)`）＋ 締切変更時の3択カード（後続もずらす／この1件だけ／戻す、逐次送信）
  2. **v2（2本目）**: 初回 prep の自動保存 `meta.planned_prep` ＋ 詳細モーダル・案件行に「予定 M/d → 今 M/d」と `completed_at` 差の日数 ＋ 案件行「余裕 N日（原因: 工程名）」（期限が先の案件のみ）
  3. **v3（3本目）**: R-128 の「今日」版1行（今日 必要Yh／枠Xh）。必要なら `buffer_days` 1入力

（全員一致ではない。悪魔の代弁者は v1 着手自体に反対を維持、理論家は末端バッファ入力の早期導入を主張したまま）
