# 03. 画面設計

## 0. アプリ全体

- **ブラウザタブタイトル**: `Youkan`（旧称JBWOSからの変更）
- **モーダル表示中の Flow 背景**: 入力応答を優先し、モーダルが開いている間だけ React Flow の animated edge を一時停止する。モーダルを閉じるとアニメーションを再開する。
- **共通モーダルの背景**: 大規模な Flow／ガント画面上でも入力応答を維持するため、`SimpleModal` の全画面背景には `backdrop-filter` を使用しない。半透明の暗幕は維持する。

---

## 1. View Mode一覧

`DashboardScreen`は`viewMode`により以下の4つのモードを切り替える。
単一のデータソースに対し、目的に応じた異なるレンズ（View）を提供する。

| モード名 | URL | 役割 | 英語名 |
|:--|:--|:--|:--|
| **登録と集中** | `/stream` | コックピット。実行(Today)と判断(Inbox)に特化 | Stream |
| **状況把握** | `/panorama` | 俯瞰。プロジェクト構造と時系列(Gantt)を確認 | Panorama |
| **全体一覧** | `/overview` | カタログ。新聞記事風にアイテムの塊を俯瞰 | Overview |
| **カレンダー** | `/calendar` | 資源管理。量感カレンダーでキャパシティ確認 | Calendar |

## 2. Stream View（登録と集中）

システムのデフォルトビュー。「今日という一日を、無理なく過ごす場所」。

### 2.1 レイアウト: 厳格な3ゾーン構成

#### Zone 1: Commit（今日の判断）
- **最大2件**のキュー
- `focus`ステータスのアイテムが表示される

#### Zone 2: Execution（今日の実行）
- **1つだけ**表示。選ばせない
- UIはシンプルなカード（例:「○○建具 | 製作中」）
- 操作: 中断(Pause)、完了(Done)のみ
- 「開始」ボタンなし（表示 = 実行中）

#### Zone 3: Life（生活）
- 画面最下部に常駐
- シンプルなチェックリスト（掃除、洗濯など）
- Executionの条件でも制約でもない。「今日の現実」を肯定的に記録するために存在

### 2.2 フィルタリング（Strict Filtering）

Inboxとfocusの完全分離:
- **Inbox List（左）**: `status: inbox`のみ。`focus`は**絶対に除外**
- **Focus Area（中央）**: `status: focus`のみ

#### プロジェクトアイテムの非表示（R-029）

- `is_project=1` のアイテムは Stream モード（Inbox / Pending / Waiting の各リスト）に**表示しない**
- プロジェクトは「見出し・構造」であり、Stream での個別作業対象とならない
- プロジェクト構造の確認・操作はパノラマ（Panorama View）・全体一覧（Overview View）で行う

### 2.3 Morning Planning（ドラッグ&ドロップ並べ替え）

- Next Strategyセクションの各`SmartItemRow`をドラッグ&ドロップで並べ替え可能
- FocusCardは常に先頭（index: 0）に固定表示
- 並べ替え完了時に自動保存
- `@dnd-kit/core` + `@dnd-kit/sortable`使用

### 2.4 主要コンポーネント

| コンポーネント | 役割 |
|:--|:--|
| `SmartItemRow` | リストアイテム表示 |
| `FocusCard` | 中央の大きなカード。DnD対応 |
| `QuickInputWidget` | **新規登録欄**。Stream/Newspaper 両画面で共通使用 |
| `SortableFocusQueue` | focusタスクのドラッグ&ドロップ並べ替えUI |
| `ViewContextBar` | フィルタ/モード表示バー |

### 2.5 新規登録欄（QuickInputWidget）のショートカット

| ショートカット | 動作 |
|:--|:--|
| `Enter` | inbox ステータスで登録 |
| `Shift+Enter` | **今日やる**（focus ステータス）で登録 |
| `Alt+Enter`（テキストあり） | inbox で登録し、すぐに詳細モーダルを開く |
| `Alt+Enter`（空欄） | 直前に登録したアイテムの詳細モーダルを開く |
| `Alt+D` | 直前に登録したアイテムの詳細モーダルを開く（後方互換） |

## 3. Panorama View（状況把握）

「いつ、どのプロジェクトが動いているか」を可視化する。

### 3.1 レイアウト: 2ペイン構成
- **左**: プロジェクト・タスクツリー
- **右**: タイムライン（Gantt）

### 3.2 実装
- コンポーネント: `PanoramaBoard`
- 大量のタスクを描画するため仮想スクロール使用

### 3.2.1 バケット構成（R-028）

パノラマの状況把握ボードは6バケット構成:

| バケット | 対応ステータス | 備考 |
|:--|:--|:--|
| Inbox | `inbox` | 未判断の投入直後 |
| Active | `focus` | 今日やる・集中対象 |
| Waiting | `waiting` | 外的要因待ち |
| Pending | `pending` | 保留（外的要因待ち）⏸ amber系 |
| 💭 Someday | `someday` | いつかやる（自発的延期） purple系 |
| Log | `done` | 完了・ログ |

- **配置順**: Inbox / Active / Waiting / Pending / 💭 Someday / Log
- Someday バケットは Pending と Log の間に配置

### 3.3 「今月を表示」ボタンの挙動
- **横方向**: タイムライン（Gantt）を水平スクロールし、今月が表示領域の中央に来るようにする
- **縦方向**: 今月が目安期間（due_date〜prep_dateの範囲）に含まれるアイテム群が表示領域の中央に来るように垂直スクロールする
- 両方向のスクロールを同時に実行し、今月に関連するアイテムが画面中央に集まるようにする

## 4. Overview View（全体一覧）

新聞記事のようにプロジェクトごとのタスクの「塊」を並べて全体像を把握する。
Ganttほど厳密ではなく、Streamほど近視眼的ではない中間ビュー。

### 4.0 初期フィルタ
- 全体一覧（Newspaper View）を開いたとき、フィルタは常に**「全て」（統合モード）**で表示する
- 他のViewからの切替時もフィルタ状態を引き継がず、「全て」にリセットする

### 4.0.1 Someday フィルタースイッチ（R-028）
- フィルターに「**Somedayを含む**」スイッチを追加
- **デフォルト: Someday を除外**（通常の作業表示に雑音を入れない）
- スイッチ ON → someday 状態のアイテムも一覧に表示される
- 目的: 「夢リスト」を明示的に見たいときだけ呼び出せる

### 4.1 レイアウト: Masonry
- CSS `column-count`によるマルチカラムレイアウト
- `break-inside: avoid`でカラムまたぎの分割を防止

### 4.2 目安時間の表示・インライン編集

- 各アイテムの納期（日付表示）の左側に**目安時間**を表示
- 表示形式: `30m`, `1.5h`, `3h` など簡潔な形式
- `estimated_minutes`が0または未設定のアイテムは非表示（スペース節約）
- **インライン編集**: 目安時間表示部分をクリック → インプットフィールドに切替
  - 簡易入力対応: `1h`, `30m`, `1.5h`, `90`（分として解釈）
  - Enter確定 / Escape キャンセル / フォーカスアウトで確定
  - API経由で即保存（`PATCH /items/{id}` の `estimated_minutes`）

### 4.3 プロジェクトヘッダーからフローへの導線

- プロジェクトヘッダーにフローチャートアイコン（GitBranch等）を表示
- クリック → そのプロジェクトのフローチャート画面に遷移
- 導線: `currentView='flows'` + `activeProjectId=プロジェクトID`

### 4.4 クリックハンドリング
- Masonryレイアウトでの`onClick`不安定問題への対策
- アイテムへのクリックは`onMouseUp`でハンドリング
- `user-select: none`を併用

### 4.5 インライン入力の挿入位置（R-060）

全体一覧（`OverviewBoard`）の「＋」ボタン押下で表示されるインライン入力欄の挿入位置と、確定後の新規アイテムの表示位置を定める。

| 項目 | 仕様 |
|:--|:--|
| インライン入力欄の位置 | 「期限なし群の末尾」（プロジェクト見出し直下ではない） |
| 確定後の表示位置 | 同じく期限なし群の末尾（`createdAt` 昇順で並ぶため最後尾） |
| 期限なし群内部ソート | 全体一覧限定で `createdAt` 昇順（登録順）。ガントビュー・パノラマボードは降順のまま変更なし |

**実装:**
- `inlineAddPosition.ts`（`getInlineAddInsertIndex`）で挿入インデックスを算出
- `HierarchyOptions.noDeadlineCreatedAsc` フラグでオプトイン
- `InlineAddRow.tsx`（新コンポーネント）でインライン入力 UI を分離
- `OverviewItem.tsx` からインライン入力状態管理を削除し `onStartInlineAdd` prop 化

## 5. Calendar View（カレンダー）

「いつが忙しいか」「どこに空きがあるか」を直感的に把握する。

### 5.0 Someday アイテムの非表示（R-028）
- `someday` 状態のアイテムはガントビュー・カレンダービュー**すべてで表示しない**
- 理由: 期限がないものは時間軸（カレンダー・ガント）に置けない
- 実装: フィルターアウト（表示オプションなし）

### 5.1 旅館カレンダー（Ryokan Style）
- 通常の時間割ではなく、旅館の予約表のように「リソース」と「日付」のマトリクスで表現
- 日付セルの背景色でタスク密度を表現（ヒートマップ）

### 5.2 サブビュー
- グリッドビュー（`RyokanGridView`）
- タイムラインビュー（`RyokanTimelineView`）
- ガントビュー（`RyokanGanttView`）

### 5.3 ガントビューの表示モード

ガントビューは「プロジェクト別」と「一覧」の2モードを切替可能。

#### スケール表示（マンスリー / ウィークリー / デイリー）（R-097, R-105でデイリー追加）

- ヘッダー（`CalendarHeader`）に「マンスリー」「ウィークリー」「デイリー」の表示モード切替トグルを配置（`ganttScaleMode: 'monthly' | 'weekly' | 'daily'`）
- 日付範囲・横スクロール挙動自体はモードによって変化しない。呼称は「列幅・行高さの記憶枠（プリセット）」を切り替えるラベル
- モードに関わらず、行方向スライダー（行高さ、既存の密度スライダー）と列方向スライダー（日付列幅、新規）の両方を常時表示
- 各モードは列幅・行高さの値を独立して記憶する（`localStorage`）。モード切替時は切替先モードの記憶値を復元して即座に反映
- マンスリーの初期値は既存動作を完全維持（列幅24px相当・既存デフォルト行高さ）。ウィークリー・デイリーの初期値は時間軸タイムラインの分解能が見えるよう広め（例: 96px）から開始し、ユーザーがスライダーで調整する
- `monthly`は従来の日次チップ表示のまま、`weekly`/`daily`は下記「時間軸タイムライン表示（R-105）」に切り替わる
- 列幅スライダーの最大値は、ガント表示エリア（日付列が並ぶスクロール可能領域、タスク一覧列を除く）の可視幅に動的に追従する（R-106）。固定pxの上限は設けず、スライダーを最大まで動かすと列1つがほぼ表示領域いっぱいになる
- 行高さスライダーのラベルは「行高」と表記する（R-106。旧ラベル「密度」から改称）

#### 時間軸タイムライン表示（R-105、R-105-Y2で表示強化）

ウィークリー/デイリー表示時、各日付セル内でタスクを「開始オフセット位置＋所要時間比例の幅」を持つブロックとして描画する（マンスリー表示の日次チップとは別表現。マンスリーは変更なし）。

- **ブロック幅**: そのアイテム・その日の割当時間(分) ÷ 1440分（24h）の比率
  - 例: 4hタスク → 24hに対し16.7%の幅
- **開始位置（その日0:00からのオフセット）**:
  - デフォルト（自動）: その日の先頭（0:00）。ただし同じ日・同じ行の中に依存関係で先行するタスクの割当があれば、その直後から配置する
  - ユーザーは横方向（時間軸方向）にドラッグしてブロックの開始位置を手動調整できる。手動調整した位置は保存され、再読み込み後も再現する
  - 保存先: `items.meta.gantt_time_blocks`（`{"YYYY-MM-DD": 開始オフセット分}`）。未調整の日はキーが存在せず自動配置にフォールバックする
- **24hはみ出し時**: その日の割当が0:00起点から数えて24:00を超える場合、ブロックの右端をその日の末尾（24:00）に揃えて描画し、警告マーク「❗️」を添える
- **稼働時間によるグレー背景は実装しない**（検討したが撤回。24h全体を通常背景のまま扱う）
- 既存の自動配置ロジック（`QuantityEngine`の日単位バックワード割当、`prep_date`ドラッグ等）はそのまま維持。今回追加するのは「その日に割り当てられた分の中で、何時何分から始まるか」という横位置情報のみで、「その日に何分割り当てられるか」自体の計算は変更しない
- **目安時間表示（R-105-Y2）**: ブロックの中央に、そのブロックの割当時間をマンスリー表示の日次チップと同様の書式（`Xh`、60分未満は非表示）で表示する
- **依存関係矢印のブロック端合わせ（R-105-Y2）**: ウィークリー/デイリー表示時、依存関係矢印の始点・終点は、日付セルの端ではなく、対応する時間軸ブロックの実際の右端（ソース側）・左端（ターゲット側）に合わせる。該当日に時間軸ブロックが存在しない場合（未配置等）は、従来どおり日付セル端にフォールバックする

#### コンテンツ印刷ボタン（R-098）

- ガント画面・全体一覧画面それぞれに「印刷」ボタンを配置
- 押下するとブラウザの印刷ダイアログが開き、ヘッダー・サイドメニュー・操作ボタン等のUIクロームを除いた本体コンテンツ（ガント本体／アイテム一覧）のみが印刷対象になる
- 専用のPDF生成・印刷ライブラリは使わず、ブラウザネイティブ`window.print()`と`@media print`CSSで実現する
- 印刷後も画面の表示状態（スクロール位置・フィルタ等）は変化しない

### 5.4 ガントビューのインタラクション

#### 目安時間インライン編集
- 左のタイトル列の右端に目安時間バッジ（`30m`, `1h` 形式）を表示
- クリックで入力欄に切替。`1h`, `30m`, `1.5h`, `90`（分）などの形式を受付
- Enter/blur で確定、Escape でキャンセル

#### マイ期限（prep_date）のクリック設定
- マイ期限が未設定のアイテムの日付セルをクリックすると、クリックした日をマイ期限として設定
- 設定後、青い割当バーが表示される

#### 右クリックメニュー
- タイトル列・青い割当バーを右クリックすると DashboardScreen と同じコンテキストメニューを表示
- メニュー表示中に `Del` キーでアイテムを完全削除

#### プロジェクト別（showGroups=true）
- プロジェクトをヘッダー行として表示し、配下のタスクをインデント表示
- プロジェクト自体が見出しの役割を持つ

#### 一覧（showGroups=false）
- **プロジェクト化されたアイテム（is_project=true）は非表示**。リーフタスクのみ表示
- 全アイテムがフラットリスト（インデントなし）
- 各アイテムのタイトル末尾に所属プロジェクト名を `[プロジェクト名]` で控えめに表示（`item.projectTitle` を使用）
- プロジェクト未所属のアイテムにはプロジェクト名を表示しない
- **ソート順**: 納期/マイ期限いずれも未設定のアイテムが先頭 → 納期・マイ期限のうち設定されている方（両方あれば早い方）の昇順

#### 完了の表示切替トグル（R-036）
- ガントビューヘッダー（`CalendarHeader`）に「完了を表示」スイッチを配置
- on: 完了済（`status=done`）アイテムを表示
- off: 完了済アイテムを非表示（フィルターアウト）
- デフォルト: on
- 状態スコープ: セッション単位（ブラウザを閉じたらデフォルトに戻る。`FilterContext` の `filterMode` と同じ思想）
- バックエンドAPI への影響なし、フロント側のフィルタとして実装

#### 完了アイテムのカレンダー要素・依存関係エッジのグレー化（R-100）
- 完了表示トグルがonのとき、完了済アイテムはタイトル文字列だけでなく（R-035の`COMPLETED_ITEM_CLASS`）、カレンダー上の視覚要素もグレー系に変える
  - 日別「割当チップ」（各日付セルに表示される小さな色付きブロック）: 完了時は`bg-indigo-500`系ではなくグレー系にする
  - 目安納期ハンドル（ドラッグ用のつまみ）: 完了時はグレー系にする
- 依存関係の矢印（エッジ）: 接続する2アイテム（source/target）のいずれかが完了済みなら、その矢印もグレー系にする（片方だけ完了のケースも含めて灰色化する、安全側の設計）
- 顧客納期（`due_date`）を示す赤い縦マーカーは対象外（アイテムの状態ではなく期日そのものを表す別概念のため、完了・未完了に関わらず赤のまま）

#### Google カレンダー予定の表示（R-039 Phase 3 UX）
- ガントビューのヘッダー（各日付列）に Google 予定の `📅` チップを最大 2 件まで表示
- 既存タスクバー（青い割当バー）と干渉しないよう、ヘッダー領域内（日付番号の下、CapacityBar の下）にスタックする
- 1 日 3 件以上の予定がある場合は末尾に「他 X 件」リンクを表示し、タップで `MobileBottomSheet` の全件展開シートを開く
- 予定チップタップで `EventDetailModal` を開く（既存 Phase 2 と同じコンポーネント）
- 設定画面の「表示するビュー」で `gantt` が OFF の場合は描画しない（取得自体を行わない）

## 5.6 量感セルの進捗棒グラフ（R-034 Phase 1, R-035）

各日付セルの下端に進捗バーを描画する。

| 項目 | 値 |
|:--|:--|
| 高さ | 4px |
| 位置 | セル下端（`absolute bottom-0`） |
| 未完了部分の色 | `emerald-500`（落ち着いた緑系） |
| 完了部分の色 | `emerald-200`（同系統の淡色） |
| 100% 超 | `red-500` で全体切替 |
| 数値表示 | なし |
| ホバーツールチップ | なし |
| 対象 | グリッドビュー（必須）、ガントビュー一覧表示（任意） |

完了アイテム所要時間も量感の分子に含めて「進捗」を表現。既存背景色グラデーション（旅館カレンダーのヒートマップ）は維持し、棒グラフは併存する。

実装:
- 新規コンポーネント `CapacityBar`（`src/features/core/youkan/components/Calendar/CapacityBar.tsx`）

#### R-042-Y1 ロード戦略（月単位キャッシュ＋ ±6 ヶ月初期取得）

- 初期取得範囲を `currentDate ± 6 ヶ月`（計 13 ヶ月）に拡大し、開いた時点で前後半年分の予定がすべてのカレンダーサブビューに即出る
- `useExternalEvents` のキャッシュ key を月単位 `YYYY-MM` に変更し、`loadedRange` / `loadMore(direction, months)` / `isLoadingMore` を新たに公開
- `loadMore` は未取得月のみを連続グループ化して 1 リクエストで fetch するため、過剰な API 呼び出しを防ぐ
- R-042-Y2 で IntersectionObserver の sentinel をグリッド／ガント／タイムラインに配置し、ロード境界 200px 手前で `loadMore` を発火する

#### R-042-Y2 IntersectionObserver sentinel 配置（lazy load 発火）

`useExternalEvents.loadMore(direction, months)` をスクロール端で自動発火するため、各カレンダービューに sentinel 要素を仕込む。共通フック `useLazyLoadSentinel` を新設し、`rootMargin` デフォルト `'200px'`（議事録 2026-06-04 §4 採用案）で IntersectionObserver を構築する。

| ビュー | スクロール軸 | sentinel 配置 | 発火内容 |
|:--|:--|:--|:--|
| グリッド | 縦 | スクロールコンテナ先頭・末尾に高さ 1px の sentinel | 先頭交差 → `loadMore('before', 3)` / 末尾交差 → `loadMore('after', 3)` |
| ガント | 横 | body の左端・右端に幅 1px の sentinel（`absolute` 配置で日付列をまたぐ） | 左端交差 → `loadMore('before', 3)` / 右端交差 → `loadMore('after', 3)` |
| タイムライン | 縦／横 | scrollRef 内部の先頭・末尾。`isMini`（縦並び）で高さ 1px、通常（横並び）で幅 1px | 同上 |

二重発火防止:

- `isLoadingMore=true` の間は `useLazyLoadSentinel` の `enabled=false` を渡し、observer 自体を作らない（既存の observer は disconnect される）
- 既キャッシュ範囲に対する `loadMore` 呼び出しは `useExternalEvents` 内部で skip 済（Y1 で対応）

経路:

- `VolumeCalendarScreen` が `useExternalEvents` から `loadMore` / `loadedRange` / `isLoadingMore` を取り出して `RyokanCalendar` に渡し、さらに各サブビューへ伝搬する。
- 各 View の props 型に `onLoadMore?: (dir: 'before' | 'after', months: number) => void` / `isLoadingMore?: boolean` を追加（オプショナル）。

注: ロード中のスケルトン UI は R-042-Y3 で別実装する。Y2 では視覚表現は触らない。

### 5.6.8 詳細モーダルのタイトル編集欄常時表示（R-037）

`DecisionDetailModal` のタイトル編集欄は、タイトルが空文字・空白文字のみ・通常文字列のいずれであっても、常に編集可能な `input` 要素として表示する。

背景:
- 旧実装は「タイトル表示用 `h2` ↔ 編集用 `input`」を `isEditingTitle` フラグで切り替えていた
- タイトルを 0 文字保存すると `h2` 表示部分自体が消え（中身が空のため空白）、再度クリックする領域も失われて編集不能になるバグが発生した

仕様:

| 項目 | 値 |
|:--|:--|
| 描画要素 | 常に `input[type="text"]` |
| プレースホルダ | `タイトル未入力`（空文字・空白のみ時の視覚ガイド） |
| 空文字保存 | 許容（`editedTitle !== item.title` であれば `onUpdate` を必ず呼ぶ） |
| 確定操作 | `onBlur` または `Enter` キー（Enter は blur をトリガー） |
| `isEditingTitle` フラグ | 廃止（モード切替自体を撤廃） |

目的: 0 文字保存後でも編集欄が消えず、ユーザーが常にタイトルを書き直せる状態を保つ。判断疲れを増やすモード切替を撤廃する。

### 5.6.7 グリッドビュー ヘッダー追従＆「今月を表示」ボタン対応（R-038）

グリッドビュー（月マス表示）でもガントビューと同様に、`CalendarHeader` の年月表示と「今月を表示」ボタンが機能する。`CalendarHeader` 自体は §5.4 の「完了の表示切替トグル」と同じく `variant: 'gantt' | 'grid'` で機能差を切り替えるが、年月表示の追従と「今月を表示」ボタンは両 variant 共通の振る舞いとして提供する。

- **ヘッダー表示**: `VolumeCalendarScreen` は `viewMode === 'gantt' || viewMode === 'grid'` のときに `CalendarHeader` を表示する（gantt: 全機能 / grid: 月切替＋今月＋日次設定のみ）。
- **縦スクロール時の追従**: `RyokanCalendar.detectVisibleMonth` がコンテナ縦中央に最も近い `data-date` 付きセルを特定し、その日付から月を算出して `onVisibleMonthChange(Date)` を発火する。`data-date` 属性は `normalizeDateKey()`（=`Date.toDateString()`）形式なので、月キーは文字列の前方一致ではなく `new Date()` でパースして取り出す（Invalid Date 防止）。
- **「今月を表示」ボタン**: `scrollToCurrentMonthCenter` のグリッド/タイムライン分岐は、今月 1 日の `data-date` を持つセルを `scrollIntoView({behavior:'smooth', block:'center'})` で中央配置する。1 日が DOM 上に存在しなければ今日のセルへフォールバックし、いずれも無ければ従来の `scrollToDateElement(now)` で代替する。`scrollIntoView` 直後に `detectVisibleMonth` を 1 度走らせ、ヘッダーの年月表示を即時同期する。
- **ガントビューの挙動は変更しない**（既存の横スクロール中心配置とアイテム群中央配置をそのまま維持）。

## 7. Flow View（フロー）

タスク間の依存関係（順序）をフローチャート風に可視化・編集する5つ目のView。
`@xyflow/react` を使用。

### 7.1 コア概念

- アイテム同士に**順序（依存関係）**を持たせる。「AのあとB」
- `parent_id`（階層）、`project_id`（所属）とは**完全に別概念**
- 依存関係は分岐・合流が可能（A→B, A→Cや、B→D, C→D）
- 循環参照（A→B→A）は禁止

### 7.2 レイアウト

- **時間軸**: 上から下へ流れる
- **ノード**: アイテムタイトルが表示されたカード
- **エッジ**: ノード間のリンク線（依存関係）。ドラッグ時に表示
- **プロジェクトグループ**: 同じプロジェクトに属するノードは薄い背景色・大枠で囲む
- **グループ間順序**: グループ同士も順序付け可能
- **独立ノード**: 順序未設定のアイテムも独立して表示可能

### 7.3 未配置アイテムリスト

- 画面右上に最前面固定表示
- フローキャンバスに未配置のアイテム一覧
- ここからドラッグ&ドロップでキャンバスに配置可能

### 7.4 操作

**マウス操作:**
- アイテムAの上にBを重ねる → 「AのあとB」のリンク構造作成（位置は移動しない）
- ノードのドラッグで位置調整
- エッジのドラッグで接続先変更
- ＋ボタンで後続ノード追加

**キーボードショートカット:**

| ショートカット | 動作 |
|:--|:--|
| `Enter` | 選択ノードの下に新規ノード追加（テキスト入力即開始） |
| `Tab` | 選択ノードから分岐して新規ノード追加（右に枝分かれ） |
| `Delete` / `Backspace` | 右クリックメニュー表示中→そのアイテムを完全削除。未表示時→選択ノード/エッジを削除 |
| `F2` | 選択ノードのタイトル編集 |
| `Escape` | 選択解除 / 編集キャンセル |
| `Ctrl+L` | 選択した2ノード間にリンク作成 |
| `Ctrl+Shift+L` | 選択ノードのリンクを解除 |
| `↑↓←→` | ノード間をフォーカス移動（依存関係に沿って） |
| `Ctrl+A` | 全ノード選択 |
| `Space` | 選択ノードの詳細モーダルを開く |
| `Home` | フロー全体がビューポートに収まるようにズームフィット |
| `Ctrl++` / `Ctrl+-` | ズームイン/アウト |
| `Ctrl+0` | ズームリセット（100%） |
| `Ctrl+I` | 未配置リストのQuick Inputにフォーカス |
| `Alt+D` | 直前に操作したノードの詳細を開く |

- 前提タスクの完了予定日より前に後続タスクを配置できない

#### 7.7.4 目安時間の全角入力対応（R-103）

- **2026-08-13 改善要望フォーム経由**。原文: 「目安時間に全角で入力したら半角に変換して認識して」
- **指揮AI事前調査済み**: `JWCADTategu.Web/src/features/core/youkan/logic/timeParser.ts`の`parseTimeInput()`が半角数字専用の正規表現（`\d`）のみでマッチしており、全角数字（`１２３`等）・全角記号（`ｈ`/`ｍ`等）を入力すると全パターンにマッチせず`null`を返す（未入力扱いになり保存されない）
- 対応: `parseTimeInput()`の冒頭で、入力文字列の全角英数字・記号を半角へ正規化してから既存の判定ロジックに通す（例: `String.prototype.normalize('NFKC')`等、標準機能での変換を優先しライブラリ追加は不要）
- 対象入力欄: フローチャート（`FlowItemNode.tsx`）・ガント（`RyokanGanttView.tsx`）・全体一覧（`OverviewBoard.tsx`等）等、`parseTimeInput()`を経由する全ての目安時間入力欄に自動的に適用される（単一の共通関数を直しているため、呼び出し元ごとの個別対応は不要）

### 7.9 コンテンツ印刷ボタン（R-101、印刷レイアウト修正: R-102）

- ガント・全体一覧（R-098）と同じく、フローチャート画面にも「印刷」ボタンを配置する
- 押下時、印刷前に既存の「全体表示」ボタン（`fitView({ padding: 0.1 })`、React Flowの`useReactFlow().fitView`）相当の処理をduration 0（即時）で実行し、全ノードが画面内に収まる状態にしてから`window.print()`を呼ぶ。ユーザーが「全体を印刷したい」と明示しているため、現在のズーム/パン位置に関わらず全ノードを収めてから印刷する
- ヘッダー・ヘルプボタン・全体表示ボタン・MiniMap・Controls（ズームUI）等のUIクロームは`.no-print`で非表示にする（既存の`@media print { .no-print { display: none !important } }`をそのまま利用）
- 印刷後、画面のズーム/パン状態が変わったままでよい（元に戻す処理は不要。ユーザーは印刷後に再度「全体表示」や個別操作で調整できる）

**R-102（2026-08-14 改善要望フォーム経由）**: 「フローチャートで印刷ボタンを押してみたら、全体が中央に印刷されていない。中央にして。」実機のスクリーンショットで、印刷プレビューの用紙右端の細い帯にフローチャート全体が押し込まれ、用紙の大部分が空白になっている症状を確認。**指揮AI事前調査済み**: `index.css`の印刷用CSS（68-72行目付近）は`.no-print`の非表示化のみで、React Flowのビューポート要素（`.react-flow`本体）を印刷用紙のサイズにフィットさせるスタイル（`@page`設定、印刷時の`width`/`height`を用紙基準に切り替える等）が存在しない。React Flowは既定でブラウザの画面表示サイズ（px単位の画面ビューポート）を基準にcanvasをレイアウトするため、印刷時にブラウザがページを用紙サイズへ再レイアウトする過程で、この画面基準のサイズ指定がそのまま持ち込まれ、用紙の一部にしか収まらなくなっている可能性が高い。実装Agentは`@media print`内で`.react-flow`関連要素の`width`/`height`を印刷コンテキストに正しくフィットさせる方法（`@page`のサイズ指定、印刷時専用のCSS上書き等）を調査し、フローチャート全体が用紙中央に収まるよう修正すること。

### 7.10 ノードへの納期・マイ期限のさりげない表示（R-104、設計検討）

- **2026-08-14 改善要望フォーム経由**。原文: 「ふろーちゃーとに、それぞれののーどのマイ期限、もしくは納期がいつになっているかもさりげなく添えるとしたらどういうやりかたにするのがいいかな？やってみてほしい」
- 提案型の要望のため、表示方法自体の設計検討を実装Agentに委ねる。以下は指揮AIの事前調査・方向性の示唆であり、最終的な見た目・配置は実装Agentの判断でよい
- **指揮AI事前調査済み**: `FlowItemNode.tsx`は既に目安時間バッジ（7.7.3、`formatMinutes(item.estimatedMinutes)`）を持っている。同様のパターンで、`item.due_date`（顧客納期）・`item.prep_date`（マイ期限）をノード下部に小さいバッジやテキストとして追加するのが自然。ガント画面（`RyokanGanttView.tsx`）の日別「目安納期ハンドル」・「顧客納期の赤マーカー」の配色（顧客納期=赤系、マイ期限=別トーン）と視覚的な一貫性を持たせることが望ましい
- 「さりげなく」という要望のニュアンスを尊重し、常時目立つ表示ではなく、未設定なら非表示（7.7.3の目安時間バッジと同じ扱い）、設定済みでも小さく控えめな表示とすること
- 両方（納期・マイ期限）が設定されている場合の表示（両方出す／どちらか優先）は実装Agentが妥当な案を判断してよい。判断に迷う場合は指揮AIに確認すること

### 7.11 複数選択まとめ移動バグ修正（R-108）

- **2026-08-17 会話内発言原文**: 「フローチャート画面でシフトをしながらドラッグすると範囲選択ができますよね　それで選択した状態でどれか要素をつかんでドラッグするとその選択をされたアイテムが全部いっぺんに相対距離を保ちながら移動できるんですけど　移動した後に何もないところをクリックして　選択解除をしたら、　全部元の位置に戻っていってしまいます　これはバグだと思うので直してほしいです」
- **期待動作**: Shift+ドラッグの範囲選択→複数ノードをまとめてドラッグ移動→キャンバスの空白部分をクリックして選択解除、という一連の操作後も、移動した位置がそのまま維持されること（選択解除で移動前の位置に戻ってはいけない）
- **指揮AI事前調査済み**: `FlowScreen.tsx`の`onNodeDragStop`（複数選択パス、L436-469付近）で各ノードの位置を`updateItemMeta`経由でサーバー保存し`setAllItems`でローカル反映後、`buildGroupNodes`で`nodes`ステートを再構築している。選択解除（`onSelectionChange`）をトリガーに、保存未反映の古い位置データで`nodes`が上書きされている可能性がある。根本原因の特定・修正方針は実装Agentが調査すること

### 7.12 日付グルーピング表示（R-109、軸をR-110で修正、R-113で表示のみに分離）

会話内発言＋手書き図により、実装着手前に使い勝手を相談したうえで仕様を確定した機能。フローチャート上のタスクを「いつまでにやるか」の日付単位でグルーピングして視覚化する。

#### トグルの配置

- 既存の右上フローティングボタン列（ヘルプ／全体表示／印刷、`absolute top-*`で縦に並ぶパターン）に「日付表示」チェックボックスを追加する
- （R-113で変更）「日付表示」チェックは**帯（日付・合計・最短）の表示ON/OFFのみ**を切り替え、ノード位置は一切変更しない。ノードを帯へ移動する操作は別ボタン「日付整列」（§7.14）に分離した
- 「元に戻す」ボタンは位置バックアップがあるとき（日付整列・自動整理の実行後）に表示する

#### 区切りの基準

- 「有効締切」＝`due_date`（顧客納期）と`prep_date`（マイ期限）のうち早い方を基準日とする（`hierarchy.ts`/`flowAutoPlace.ts`の`getEffectiveDeadline`と同じ考え方）
- 有効締切が未設定のアイテムの扱いは実装Agentが妥当な案を判断してよい（例: 「未定」区間を末尾に設ける等）。判断に迷う場合は指揮AIに確認すること

#### 表示（R-110で軸を修正）

- y軸（縦）を日付軸とし、有効締切の早い順に上から下へ帯を積み上げる。帯はフロー全体のコンテンツ幅いっぱいの横長帯とし、帯同士は横線（下端の罫線）で区切り、区間ごとに背景色を変えて視覚的に区別する
- 各日付区間（帯）内のノード配置（R-111で修正）: 元のマインドマップの形をできるだけ変えないため、**ノードの横位置（`flow_x`）は一切変更せず、縦方向の移動だけで該当日付の帯の中へ収める**
  - 帯内では各ノードに「行」を割り当て、`flow_y = 帯の上端 + 上パディング + 行番号 × 行間隔` とする
  - 行の決め方: 依存関係を優先する。帯内の依存元ノードの行より下の行を下限とし、そこから順に見て、横区間（`flow_x`〜`flow_x + ノード幅`）が既に置かれたノードと重ならない最初の行に置く。横に重ならないノード同士は同じ行に詰める（隙間を作らない）
  - 処理順は依存の深さ順（`computeDepthWithin`）→同じ深さなら元の`flow_y`順（元の上下関係を保つ）
  - 帯の高さは行数に応じて可変（左上3行ラベルが収まる最小高さを下限とする）。各帯のyは前の帯の下端から累積する
  - 帯の横幅は案件（`projectId`）ごとの全ノードのX範囲（最小X − ラベル余白 〜 最大X + ノード幅）で、同じ案件の帯どうしは共通（R-122、詳細は§7.18）
  - （R-110時点では帯内を依存深さ順に左から右へ横一列に並べ直していたが、元のマップの形が壊れるためR-111で上記に変更した）
- 各帯の左上に、日付（曜日つき）→改行→合計時間→改行→最短時間、の順で縦に3行表示する（未完了タスクがある区間は下記「残り時間」の4行目が加わる）:
  - **合計時間**: その日が有効締切のタスクの目安時間（`estimatedMinutes`）を単純合計した値
  - **最短時間**: その区間内のタスクだけを対象にした依存関係グラフのクリティカルパス（最長経路）。区間をまたぐ依存関係（前日のタスクの後続としてこの区間のタスクがある、等）は計算に含めない。並列に実行可能な分岐は最大値を採用し、直列の依存は合計する
  - 手書き図の例: 3ノード直列の区間は「合計4h」（＝クリティカルパスと一致）。分岐＋合流のある区間は「合計7h」（全タスクの単純合計）「最短4.5h」（クリティカルパス、並列分岐の遅い方の経路時間）
  - **残り時間（R-117）**: その区間内に未完了（`status !== 'done'`）のタスクが1件以上あるときだけ、「最短」の下に4行目として「残り Xh」を表示する。値は未完了タスクの目安時間（`estimatedMinutes`）の単純合計（依存関係は考慮しない）。区間内が全て完了済みのときは表示しない
- （R-109時点の初期実装ではx軸を日付軸・帯内をy軸方向の配置としていたが、フローチャート本来の「上から下へ流れる」向きと逆であったため、上記のとおりR-110で軸を入れ替えた）

#### 帯の位置と表示（R-113で「表示のみ」に変更、幅の基準はR-122で案件単位に変更）

- チェックONは帯を重ねて表示するだけで、ノードの`flow_x`/`flow_y`は書き換えない
- 各帯の**上端・下端（y/height）**は、その日付グループに属するノードの現在位置の外接矩形に追従する: 上端＝最も上のノードの`flow_y`−上パディング、下端＝最も下のノードの下端＋下パディング（ノードの幅・高さはReact Flowの実測値、未計測時は既定値）。最上部・最下部のノードをドラッグすれば帯もそれに合わせて動く（ライブ更新）
- 各帯の**左端・右端（x/width）**は、R-122により日付グループ単独ではなく**同じ案件（`projectId`）に属する全ノード**の現在位置の外接矩形を基準にする: 左端＝案件内で最も左のノードの`flow_x`−ラベル余白、右端＝案件内で最も右のノードの右端。同じ案件の帯はすべて同じx/widthになる（詳細・確定仕様は§7.18）
- 帯同士は重なってもよい（半透明の重ね表示）。「日付整列」（§7.14）を実行すると各帯が上から下へ日付順に積み上がった状態になる
- 帯の内容（日付・合計・最短）と位置は、ON中にアイテム・依存関係・ノード位置が変わったら再計算する
- チェックOFFは帯を消すだけ（ノード位置は不変）
- ON中でもノードのドラッグ（横・縦とも）は通常どおり許可する。自動整理（§7.13）もON中に使える

（R-109〜R-112時点ではチェックONで実際にノード位置を日付配置へ書き換え、「元に戻す」で復元する仕様だったが、R-113で「表示」と「移動」をボタンに分離した）

### 7.13 自動整理ボタン（R-112）

会話内発言「マインドマップに自動整理ボタンを追加しよう。フローチャートがそれぞれが重ならず、エッジ同士も重なりが少ない位置関係、そしてノード同士の隙間もできるだけエッジが見やすい範囲で狭く」「自動整理も日付表示と同じように、戻るができる仕様に」に基づく。

#### ボタンの配置

- 右上フローティングボタン列（ヘルプ／全体／印刷／日付表示／元に戻す）の続き（`top-[180px] right-3`）に「自動整理」ボタンを置く
- 日付表示チェックON中も使用可（R-113で変更。「自動整理」で横並びを整えてから「日付整列」で縦を日付に合わせる、という順序で使える）
- 既存の「全て自動配置」ボタン（未配置アイテムがある時に未配置リスト内に出るもの）は変更しない

#### 配置アルゴリズム（自前実装・外部レイアウトライブラリは使わない）

1. プロジェクトごとにグラフを分けて整理し、プロジェクトを横に並べる（前プロジェクトの実幅＋一定の隙間で累積）。プロジェクト未所属のアイテムは最後のグループ
2. 層分け（縦方向）: 依存関係のLongest Path Layering。依存元が上・依存先が下（既存の上→下の流れに合わせる）
3. 層内の並び順: 初期順は元の`flow_x`順（元の左右関係を尊重）。隣接層の接続先の平均位置で並べ替える重心法を上下方向に数回繰り返し、エッジの交差を減らす
4. 座標: 層内は左から順にノードの実測幅＋狭い横間隔で詰め、各層はプロジェクト内で中央揃え。縦は層ごとの最大高さ＋縦間隔を累積。ノードサイズはReact Flowの実測値（`node.measured`）を使い、未計測時は既定値
5. 依存のない孤立ノードは最上段に元の`flow_x`順で並ぶ

#### 縦間隔スライダー（R-114）

- 「自動整理」ボタンの近くに縦間隔（層と層の隙間`GAP_Y`）を変えるスライダーを置く。範囲はおおむね10〜100px、既定値は35px（R-112時点の60pxの約60%）
- 値は`localStorage`（キー`youkan_flow_arrange_gap_y`）に記憶し、次回以降も使う
- 「自動整理」を押すとその値でプレビューへ入る（§7.17）。プレビュー中にスライダーを操作するとリアルタイムに再計算する（R-120）。プレビューを開いていないときの操作は次回「自動整理」を押したときの初期値としてのみ反映する

#### Undo

- 実行前に全配置ノードの位置を退避し（日付整列と同じバックアップ機構）、「元に戻す」で1段階復元する

### 7.14 日付整列ボタン（R-113）

会話内発言「日付表示はONOFF表示切替のみで動かさない。それとはべつで、自動調整ボタンと、それとは別で日付を意識した位置に上下方向だけ移動するボタンを作ってほしい」に基づく。

- 右上フローティングボタン列に「日付整列」ボタンを追加する（「自動整理」の下）
- 押すと、R-111で確定した帯内配置ルール（§7.12「各日付区間（帯）内のノード配置」）どおりに、**有効締切のあるノードは横位置を変えず縦方向だけ**該当日付の区間へ移動し保存する（区間は日付順に上から下へ、区間の高さは行数で可変、y原点は押下時点の有効締切のあるノードの最小`flow_y`−上パディング）。移動後は§7.12の帯（外接矩形）が自然に上から下へ積み上がる
- 日付表示のON/OFFにかかわらず使える。実行しても日付表示のON/OFFは変えない
- 実行前に全配置ノードの位置を退避し「元に戻す」で1段階復元する（自動整理と共通の機構）

#### 日付未定ノードの配置（R-115）

- 有効締切のあるノードとは扱いを分ける。**日付未定のノードは、日付順の帯の並び（縦積み）とは別に、その左側に専用の1列（縦方向のみの単一カラム）として配置する**
- 専用列のX位置: 有効締切のあるノードの中で最も左にあるノードの`flow_x`から、帯のラベル余白と間隔ぶん左に離す（帯の左上ラベルと重ならない位置）
- 専用列のY位置: 列全体の高さ（未定ノードの件数×行間隔）を、日付順の帯を全て積み上げた合計の高さに対して**縦中央揃え**にする（「左中央へ配置」）
- 列内のノードの並び順・行の割り当ては、依存関係がある場合は依存元を上・依存先を下にする（帯内と同じ考え方）。依存がなければ元の上下関係（`flow_y`）を保つ
- 有効締切のあるノードが1件もない場合は、専用列だけを画面左上を起点に縦に並べる

#### ノード間の上下幅スライダー（R-115）

- 「日付整列」ボタンの近くに、帯内でノードを縦に並べる行間隔（`ROW_HEIGHT`。日付未定の専用列にも同じ値を使う）を変えるスライダーを置く。範囲はおおむね40〜220px、既定値は110px（R-111時点の固定値を踏襲）
- 値は`localStorage`（キー`youkan_flow_date_align_row_height`）に記憶し、次回以降も使う
- 「日付整列」を押すとその値でプレビューへ入る（§7.17）。プレビュー中にスライダーを操作するとリアルタイムに再計算する（R-120）。プレビューを開いていないときの操作は次回「日付整列」を押したときの初期値としてのみ反映する

### 7.15 フロー操作パネルのホバーツールチップ（R-116）

会話内発言「スライダーやボタンなどフローチャート上のボタンたちの上にマウスを乗せて1秒待つとヒントでなにをするものか表示するようにして」に基づく。

- 右上フローティングボタン列・スライダー群（新規タスク追加／ヘルプ／全体表示／印刷／日付表示チェック／元に戻す／自動整理とその縦間隔スライダー／日付整列とその上下幅スライダー）に、共通のホバーツールチップを付ける
- マウスをボタン・スライダーの上に乗せてから約1秒（1000ms）経過したら、何をするボタンかを短い日本語ラベルで表示する。マウスが離れたら即座に消える
- ブラウザ標準の`title`属性（表示タイミング・見た目が環境依存で統一されない）には頼らず、共通の小さなツールチップ部品を作って使い回す
- 表示内容は各ボタンの既存の`title`文言をそのまま使ってよい（例:「自動整理の縦間隔」「横位置は変えず、縦方向だけ日付の区間へ整列」等）

### 7.16 「詰める」機能（R-118、横方向圧縮をR-120で追加）

会話内発言＋スクリーンショット添付「この状態のフローチャートから、上下方向をできるだけつめる。ただしえっじがみえるはんい、エッジの曲がりが潰れて見づらくなるのは回避できる範囲で」「これは自動整理したあと、手動でいい感じにみやすく調整したところです」に基づく。「自動整理」（§7.13）が並べ替え・交差削減まで行うのに対し、「詰める」は**現在の並び順を一切変えず**、ノード間の隙間だけを詰める。手動で微調整した後の仕上げに使う想定。プレビュー→保存確定の操作フローはR-120で追加（§7.17参照）。

#### ボタンの配置

- 右上フローティングボタン列に「詰める」ボタンを追加する（「日付整列」の下）
- 押すと§7.17のプレビューパネルが開く。パネルには縦間隔スライダー・横間隔スライダーと、それぞれの有効/無効チェックボックスを置く（R-120）
- 縦間隔の既定値は「自動整理」の縦間隔スライダー（`GAP_Y`、§7.13）と同じ値を初期値にする

#### アルゴリズム（縦方向、R-118）

- 対象ノードを現在の`flow_y`昇順で処理する（元の上下の並び順は変えない）
- 各ノードについて、以下のうち最も下にある位置の直下（縦間隔ぶん空けて）まで引き上げる（新しい`flow_y`の下限とする）:
  1. 横（X区間）が重なる、既に新しい位置が決まったノードの下端
  2. 依存元ノードの新しい位置の下端
- 横位置（`flow_x`）は変更しない。ノード同士のX区間が重ならなければ独立して詰められる
- 依存元ノード・横に重なるノードとの間には常に縦間隔以上の隙間を確保するため、エッジが極端に押しつぶされて見づらくなることを避けられる

#### アルゴリズム（横方向、R-120で追加）

- 縦方向の考え方をそのまま横に倒したもの。対象ノードを現在の`flow_x`昇順で処理する（元の左右の並び順は変えない）
- 各ノードについて、縦（Y区間）が重なる、既に新しい位置が決まったノードの右端 + 横間隔まで左へ寄せる（新しい`flow_x`の下限とする）。制約が無ければ現在の`flow_x`のまま
- 依存関係は使わない（フローの依存は上→下の縦方向の意味しか持たないため、横方向の圧縮では考慮しない）
- 縦・横の両方が有効なときは、縦方向の圧縮結果（新しい`flow_y`）を確定させたうえで、その結果に対して横方向の圧縮を適用する

#### チェックボックスによる有効/無効（R-120）

- 縦間隔・横間隔それぞれにチェックボックスを置き、チェックOFFのときはその軸の圧縮を行わない（元の座標のまま）。両方OFFなら「詰める」は何も変更しない
- チェックON/OFFやスライダーの値を変えるたびに、§7.17のプレビューにリアルタイムで反映する

### 7.17 配置系ボタンのプレビュー→保存確定方式への統一（R-120）

会話内発言「詰めるボタンを押したら縦と横のスライダーと保存ボタンがでて、それをリアルタイムで動くのを見ながら調整して、保存ボタンを押すと確定。こういう流れが良い」に基づく。対象は「自動整理」（§7.13）・「日付整列」（§7.14）・「詰める」（§7.16）の3ボタン。これまでの「押すと即座に保存し、必要なら『元に戻す』で1段階Undo」という方式を廃止し、以下のプレビュー方式に統一する。

#### 操作フロー

1. いずれかのボタンを押すと、その場でプレビューパネル（そのボタン固有のスライダー群＋「保存」「キャンセル」ボタン）を開く
2. パネルを開いた時点のスライダー既定値で即座に配置を計算し、キャンバス上のノード位置を**ローカル表示だけ**書き換えてプレビューする（サーバーへは送信しない）
3. スライダーの値やチェックボックスを操作するたびに再計算し、リアルタイムでプレビューを更新する
4. 「保存」を押すと、その時点のプレビュー位置を実際に保存する（既存の`applyPlacements`、保存前の位置は退避して「元に戻す」で1段階復元できるようにする＝保存後のUndoは従来どおり残す）。パネルを閉じる。座標PUTは`savePlacementsSequentially`（R-121）を経由して1件ずつ逐次送信する（本番環境でSQLiteの単一ライターロックへ数十件のPUTが同時に殺到し保存失敗する不具合の対策。詳細は`docs/requests_log.md` R-121参照）
5. 「キャンセル」を押すと、プレビュー前の位置に戻してパネルを閉じる（サーバーへは何も送信していないため、Undoの操作は不要）
6. あるボタンのプレビュー中に別の配置系ボタンを押した場合は、開いていたプレビューをキャンセル扱いで閉じてから新しいプレビューを開く（同時に2つ開かない）

#### 各ボタンのプレビュー内容

- **自動整理**: 既存の縦間隔スライダー（`GAP_Y`）のみ
- **日付整列**: 既存の行間隔スライダー（`ROW_HEIGHT`）のみ
- **詰める**: 縦間隔・横間隔の2つのスライダーと、それぞれの有効/無効チェックボックス（§7.16）

#### 日付表示の帯との関係

- 日付表示（§7.12）がONのとき、プレビュー中も帯はノードのライブ位置（プレビュー位置）に追従してよい（`calculateDateBands`は既に実位置ベースで計算しているため、追加対応なしで動く想定）

### 7.18 日付表示の帯幅を案件（プロジェクト）単位へ拡張（R-122）

発注者発言原文: 「日付表示をした時の日付のその帯のものの幅はそのフローチャートの全体幅にして下さいそのプロジェクトの枠でいいんで（中略）そのプロジェクトの左端に、何日に何時間という情報がならんでいて見やすいとおもいます」。確認往復2回を経て、帯幅の基準を「案件（`projectId`）ごとの全ノードの外接矩形幅」に確定した。

#### 確定仕様

1. 日付表示ONの帯幅（x/width）は、§7.12で「その日付グループに属するノードの外接矩形」としていたものを、**案件（`item.projectId`）に属する全ノード（日付を問わず）の外接矩形幅**へ変更する。プロジェクトフォーカス中（案件1件のみ表示）でもフォーカスなし（全案件表示）でも同じ基準を適用する。フォーカスなし時に画面へ複数案件が混在していても、**同じ日付でも案件が異なれば案件をまたいでまとめず、別々の帯**として、それぞれの案件のノード位置に応じたx/widthで表示する（帯のReactノードIDも`dateband-{projectId}-{dateKey}`とし、同日付・別案件での衝突を避ける）
2. `projectId`が無いアイテム（個人タスク等）は、案件に属さない1つの仮想グループとしてまとめて扱う（互いに案件をまたぐ扱いにはしない）
3. 日付未定の専用列（帯の左外側に別配置、§7.14「日付未定ノードの配置（R-115）」）は本変更の対象外。案件が混在していても分割せず、現状どおり1つの帯のまま・幅も統一しない（`calculateDateBands`は`UNDATED_KEY`グループを案件分割ロジックの外側で従来どおり計算する）
4. y/height（上端・下端）は引き続き**その日付グループ単独**のノードの外接矩形（変更なし）。x/widthだけが案件単位に変わる
5. **サブプロジェクト（`isProject`で子タスクをコンテナ化したアイテム、`parentId`で表現される入れ子構造）への対応は本要望のスコープ外として見送った。** 発注者の温度感は「たぶんできると思うけど」という非必須の確認で、実装Agentの技術調査の結果、以下の理由により小さくない複雑化を伴うと判断したため:
   - フロー画面には現状、`isProject`/`parentId`から「あるノードがどのサブプロジェクトに属するか」を解決する仕組みが存在しない（`isProject`はプロジェクト化トグル操作にのみ使われている）。サブプロジェクト単位で帯を分割するには、案件内の全ノードを`parentId`で辿って直近の`isProject`祖先を求める木構造解決処理を新設する必要がある
   - `useYoukanViewModel.ts`の新規アイテム作成ロジック（L1328）は、親が`isProject`のとき子の`projectId`を親自身のIDに差し替える場合があり、`projectId`の意味が「トップレベル案件」と「サブプロジェクト」で作成経路によって揺れる可能性がある。既存データでこの前提が一貫している保証がなく、サブプロジェクト判定を`projectId`だけで安全に行えない
   - 多段ネスト（サブプロジェクトの中にサブプロジェクト）を考慮すると、帯の分割・幅計算・y/height計算が再帰的に必要になり、`flowDateGrouping.ts`の複雑度が大きく増す
   - 上記に対し、案件（`projectId`）単位の分割は既存の`buildGroupNodes`（`flowGrouping.ts`、プロジェクト背景枠の描画）と同じ「`projectId`でグルーピングし全ノードの外接矩形を取る」パターンをそのまま流用でき、追加の複雑さがほぼない

#### 実装

`logic/flowDateGrouping.ts`の`calculateDateBands`を、日付グループごとの単純な外接矩形計算から、「日付が確定しているアイテムを`projectId`（無ければ仮想キー）でグルーピング→案件ごとにX方向の外接矩形（`calculateProjectXBounds`）を先に求める→案件×日付の組み合わせごとに帯を1件生成し、x/widthは案件全体の外接矩形、y/heightはその日付グループ単独の外接矩形を使う」という2段階の計算に変更した。日付未定グループ（`UNDATED_KEY`）はこの案件分割の対象外とし、従来どおり全アイテムをまとめた1つの外接矩形のまま計算する。`DateBand`型に`projectId: string | null`を追加し、`FlowScreen.tsx`側のReactノードID生成にも反映した。

**エラー表示:**
- リフレッシュトークン失効: 「Google 側で連携が解除されました。再連携してください」と表示し、未連携表示に切り替え

**R-072（未実装だった失効検知の実装）:** 上記「リフレッシュトークン失効」表示は仕様として書かれていたが、実装時に `invalid_grant` を判別する処理自体が漏れていたため機能していなかった（本番で `invalid_grant` エラーが継続発生し、`/google/calendars` は生の500エラー、自動同期経路はエラーを握りつぶしてキャッシュにフォールバックし続けるだけで、どちらもこの失効表示に到達しなかった）。

- `GoogleCalendarService::refreshAccessToken()` がGoogleのエラーレスポンスから `error === 'invalid_grant'` を判別し、`user_google_oauth.invalidated_at`/`last_error`（§3.6）に記録する
- `invalidated_at` が非NULLの間は自動同期（`GET /google/calendar/events` の裏側の自動リフレッシュ）を試行せず、既存キャッシュのみ返す
- 設定画面の連携状態取得（`GoogleCalendarSection` の初期表示・ポーリング）で `invalidated_at` の有無を見て、非NULLなら上記の「Google 側で連携が解除されました。再連携してください」表示に切り替える（「今すぐ更新」ボタンは「Google で再ログイン」に変わり、`POST /api/google/oauth/start` を叩く）
- **既知の根本原因**: OAuth同意画面が「テスト中」ステータスのままだとリフレッシュトークンが7日で強制失効する。Google Cloud Consoleでの「本番公開」への切り替えは発注者本人のみが行える作業のため、この実装はあくまで検知・UX側の対症療法であることに留意する

## 13. 担当者別ビュー（AssigneeView、R-050 Phase1）

会社の代表・管理者が「誰が何を抱えているか」を一望するための画面。個人の生活タスクとは無関係のため**会社コンテキスト（テナント選択時）限定**で、個人モードでは画面自体を表示しない（メニュー項目も出さない）。

会議決定（`docs/kaigi/2026-07-09-R050テナント型AI中枢設計.md` 8節ステップ3）・バックエンド引き継ぎ（`docs/handover/R-050-phase1-backend.md`）に基づく。画面4（社員向けToday）とは統合しない独立画面。

### 13.1 アクセス経路

- `ViewState = 'assigneeView'`（8節の表に追記済み）
- `YoukanHeader` または `MenuDrawer` の会社コンテキスト時のみ表示される項目として導線を追加する（個人モード時は非表示）。具体的な設置場所は既存の `companySettings`/`userlist` 導線と横並びで実装Agentが判断してよい。

### 13.2 デフォルト表示（本人分のみ）

- 初期状態は常に `GET /items?scope=team&assigned_to=<自分のuserId>`（`useAuth().user.id` 相当、`u_...` 形式）を呼ぶ。
  - バックエンド仕様上 `assigned_to === currentUserId` の指定は誰でも許可されるため、非管理者でもこの初期表示は成功する（403にならない）。
  - 既存の可視性ルール1〜3（created_by=自分 OR assigned_to=自分）ではなく、あえて `assigned_to=自分` のみに絞る（「既存の assigned_to を中心に表示する」という要件どおり、自分が作成しただけで担当者が別人のアイテムは含めない）。
- 個人モード（`useAuth().tenant === null`）では画面遷移不可・非表示。

### 13.3 管理者による担当者切り替え

- `useAuth().tenant.role` が `'owner'` または `'admin'` の場合のみ、担当者チップ／タブの切り替えUIを表示する。それ以外のロールでは自分の名前のみを静的に表示し、切り替えUIそのものを描画しない。
- 切り替え候補は2種類をマージして1つのチップ列に表示する:
  1. **テナットメンバー（`assigneeKind: 'user'`）**: `GET /tenant/members`（`CompanySettingsScreen.tsx` と同じ呼び出し方。`ApiClient.getMembers()` は `/members` を叩いており実体が `/tenant/members` ではないため使用しないこと）のレスポンスの `userId`（＝`u_...`形式、`assigned_to`にそのまま使える）と `display_name` を使う。
  2. **assignees由来（`assigneeKind: 'assignee'`）**: 既存の `useAssignees()`（`src/features/core/youkan/hooks/useAssignees.ts`）をそのまま再利用し、`id`（整数文字列）と `name` を使う。
  - 自分自身のチップは常に先頭固定（pinned）。
- チップ選択で `assigned_to` を切り替えて `GET /items?scope=team&assigned_to=<選択ID>` を再取得する。403（Access Denied）/404（Assignee not found）が返った場合はトースト表示のうえ自分の担当分表示にフォールバックする。

### 13.4 レイアウト

```
┌─────────────────────────────────────────────┐
│ 担当者別ビュー                                │
│ [松井さん] [晴樹] [宗三] ...  ← 管理者のみ表示  │
├─────────────────────────────────────────────┤
│ 松井さん                                      │
│  今日の所要時間: 320 / 480分（67%）           │
│  未完了 5 ／ 詰まり 1 ／ 待ち 2                │
│                                               │
│  今日                                         │
│  □ 長浜町案件 障子4枚 剥がし  60分            │
│  □ 梶本様案件 框戸 材料取り   90分            │
│                                               │
│  明日                                         │
│  □ 障子貼り補助               90分            │
│                                               │
│  今週                                         │
│  □ 組子案件 デザイン確認     120分            │
└─────────────────────────────────────────────┘
```

- タスク行は必ず**案件名（プロジェクト名）とセット**で表示する（`item.parentTitle` または `item.projectId` を辿って解決したプロジェクト名。既存 `Newspaper View` 等での案件名解決ロジックを参照・再利用すること）。案件に属さないタスクは案件名部分を省略。
- 各タスク行に `estimated_minutes`（目安時間）を表示。

### 13.5 日付バケット分類（今日／明日／今週）

`due_date`（`YYYY-MM-DD`）を基準に、`date-fns` と既存 `dateUtils.ts`（`safeParseDate` 等）を用いて以下3バケットに分類する新規純関数を実装する（例: `logic/assigneeViewBuckets.ts`）:

| バケット | 条件 |
|:--|:--|
| 今日 | `due_date` が本日 |
| 明日 | `due_date` が翌日 |
| 今週 | `due_date` が「明後日〜今週末（日曜起点/月曜起点は既存カレンダー実装の週起点定義に合わせる）」の範囲内 |

- `due_date` が無い（null）アイテムは Phase1 では非表示でよい（担当者別ビューは期限ドリブンの一覧のため）。
- 完了済み（`status === 'done'`）アイテムは3バケットに含めない。

### 13.6 所要時間合計・キャパ比率

- 「今日」バケットの `estimated_minutes` 合計を所要時間合計とする。
- 分母（キャパシティ）は `GET /tenant/members` の該当メンバーの `dailyCapacityMinutes`（`capacityProfile` があればそちらを優先、量感カレンダーの分母ルール `docs/spec/06_変更履歴.md`「2026-07-06: 量感カレンダー分母ルールの確定」に合わせる）。`assigneeKind: 'assignee'`（メンバーでない外注等）の場合は分母データが無いため比率表示自体を省略し、所要時間合計のみ表示する。
- 比率表示は評価語（「超過」「余裕あり」等）を使わず、数値と割合のみを淡々と表示する（`docs/reference/vision/R050_Tenant_AI_Business_OS.md` に記載の「非審判原則との文言矛盾」指摘を踏まえ、Phase1では評価語を採用しない）。

### 13.7 未完了・詰まり・待ち状態

Phase1では既存の `JudgmentStatus` のみで以下のように定義する（新規ステータス追加はしない）:

| 表示ラベル | 集計条件（選択中の担当者の全アイテム対象、バケット外も含む） |
|:--|:--|
| 未完了 | `status !== 'done'` の件数 |
| 詰まり | `status !== 'done'` かつ `due_date` が本日より過去（期限超過）の件数 |
| 待ち | `status === 'waiting'` の件数 |

### 13.8 コンポーネント構成（MVVM）

- View: `src/features/core/youkan/screens/AssigneeViewScreen.tsx`（新規）
- ViewModel: `src/features/core/youkan/hooks/useAssigneeView.ts`（新規。担当者候補の取得・選択状態・アイテム取得・バケット分類・集計を担う）
- Model/純粋ロジック: `src/features/core/youkan/logic/assigneeViewBuckets.ts`（新規。日付バケット分類・集計関数。VMから分離してユニットテストしやすくする）
- API拡張: `ApiClient.getAllItems()`（`src/api/client.ts`）の `scope` 型に `'team'` を追加し、`assigned_to` オプションを追加する（既存のURLSearchParams構築パターンを踏襲）。新規の生 `fetch` は書かないこと。
- 型拡張: `Item` 型（`src/features/core/youkan/types.ts`）に `assigneeKind?: 'user' | 'assignee' | null` を追加する。

### 13.9 除外事項（Phase1スコープ外）

- AI割り振り提案・meta.dispatch関連UI・承認/却下フローは含めない。
- 画面4（社員向けToday）との統合はしない。
- 本格的なRBAC設計はしない（`tenant.role` によるフロント側の表示分岐のみ）。

思いついた瞬間にスクリーンショット付きで改善要望を送れる、低摩擦な入力口。

  - ロゴ文字サイズ: `text-sm`（14px）→ `text-[7px]`（7px、ちょうど50%。同ヘッダー内の最小表記サイズと統一）
  - ボタンはアイコン+短いラベル、または既存の `ForAiButton.tsx` パターンに倣いアイコンのみ＋`title`属性
- **スマホ**: `MenuDrawer.tsx` の「ツール」セクション（`onOpenForAi` の隣）に `MenuItem` として追加

### 14.2 モーダル

- `SimpleModal` をベースに新規 `ImprovementRequestModal.tsx` を作成（`ForAiModal.tsx` を実装テンプレートとする）
- 入力項目:
  - 本文テキスト（`<textarea>`、必須、空/空白のみは送信不可）
  - 画像添付（任意、1枚まで、5MBまで、`image/png`・`image/jpeg`・`image/webp`）。ファイル選択に加え、クリップボード貼り付け（`onPaste`）にも対応してスクリーンショットを直接貼れるようにする

### 14.3 データフローと保存先（重要）

- 送信は認証必須（`useAuth()` の現在のユーザー情報を利用）
- サーバー側は送信内容を **サーバーローカルの `docs/requests_sub.md`** に直接追記する。git管理下のファイルではなく、あくまでサーバー上の実体であることに注意（詳細: `04_データ設計.md` §3.9）
- 画像はサーバーローカルのディレクトリに保存し、`requests_sub.md` からは相対パスまたはURLで参照する
- **回収は手動運用**: 発注者または指揮AIが不定期にSSH/scpでサーバーへアクセスし、`docs/requests_sub.md`と画像をローカル（gitリポジトリ）へダウンロードする。自動同期・自動プルAPIは持たない
- 回収後、内容を読んで良いと判断した項目は `docs/requests.md` に人力で書き写す（そこから通常のSdDDフローでR-ID採番・仕様化に進む）
