**`capacity_profile` JSON:**

```json
{
  "standardWeeklyPattern": { "1": 480, "2": 480, "3": 480, "4": 480, "5": 480 },
  "exceptions": { "2026-02-09": 240 },
  "defaultCompanyWeeklyPattern": { "1": { "tenant-a": 240 } },
  "dailyCompanyExceptions": { "2026-02-09": { "tenant-a": 0 } }
}
```

- `standardWeeklyPattern`: このテナントへ提供する曜日別キャパシティ。未設定日は `daily_capacity_minutes` を使う
- `exceptions`: 日別の総量例外。0 分の日は会社/チーム分母に含めない
- `defaultCompanyWeeklyPattern` / `dailyCompanyExceptions`: 複数会社配分を扱うための拡張。対象テナントIDの値があれば最優先する
- 会社/チームスコープの量感分母は、`is_core=1` のメンバーについて上記ルールで日別キャパシティを算出し、合計する

### 3.5 item_dependencies テーブル

アイテム間の依存関係（順序）を管理する。フローView用。
`parent_id`（階層）、`project_id`（所属）とは完全に別概念。

| カラム | 型 | 説明 |
|:--|:--|:--|
| `id` | TEXT PK | UUIDv7 |
| `tenant_id` | TEXT | テナント隔離 |
| `source_item_id` | TEXT NOT NULL | 上流（先にやるタスク） |
| `target_item_id` | TEXT NOT NULL | 下流（後にやるタスク） |
| `created_at` | INTEGER | 作成日時 |

**制約:**
- `UNIQUE(source_item_id, target_item_id)` — 同じペアの重複登録を防止
- 循環参照（A→B→A）はアプリケーション層で防止
- `FOREIGN KEY` で items テーブルを参照

**フロー位置情報:**
- `items.meta` JSON に `{ "flow_x": 250, "flow_y": 100 }` として格納
- 新カラムは追加しない（既存の meta カラムを活用）

**ガント時間軸タイムラインのブロック位置（R-105）:**
- `items.meta` JSON に `{ "gantt_time_blocks": { "2026-08-20": 540, "2026-08-21": 0 } }` として格納。キーは `YYYY-MM-DD`、値はその日の0:00からの開始オフセット分（0〜1439）
- ユーザーが時間軸タイムライン上でブロックをドラッグして手動調整した日のみキーを持つ。キーが存在しない日は自動配置（その日の先頭、または同日内の依存タスク直後）にフォールバックする
- `flow_x`/`flow_y`と同じ `meta` カラムを共有するため、新カラム・新テーブルは追加しない

**API露出（R-099）:**
- `GET /items`系のレスポンス各アイテムに、`dependsOn: string[]`（自分の前提となるアイテムIDの配列。自分がtargetになっている行のsource_item_id群）・`blocks: string[]`（自分が前提になっているアイテムIDの配列。自分がsourceになっている行のtarget_item_id群）を追加する
- 目的: `GET /dependencies`を別途叩いて`GET /items`と突き合わせなくても、依存グラフをAPIレスポンス単体から読めるようにする（AI等の外部クライアントが1回のリクエストで依存関係を把握できるようにするため）
- 実装上の注意: 1アイテムずつクエリを発行するN+1は禁止。`DependencyController::getDependenciesDirect()`と同じテナントスコープの絞り込みで対象テナント分の`item_dependencies`を一括取得し、メモリ上でアイテムIDごとの隣接リストを構築してから各アイテムのJSONに埋め込むこと
- 依存関係を持たないアイテムが大半のため、両フィールドとも空配列`[]`がデフォルト

### 3.6 user_google_oauth テーブル（R-034 Phase 2）

ユーザーごとに Google OAuth のリフレッシュトークンと primary カレンダー情報を保管する。

| カラム | 型 | 説明 |
|:--|:--|:--|
| `user_id` | TEXT PK | users.user_id への外部キー（1 user 1 行） |
| `encrypted_refresh_token` | BLOB NOT NULL | AES-256-GCM 暗号化済みリフレッシュトークン |
| `primary_calendar_email` | TEXT | 連携した Google アカウントのメール（UI 表示用） |
| `primary_calendar_id` | TEXT | primary カレンダーの calendar_id |
| `last_sync_at` | INTEGER | 最終同期時刻（Unix epoch sec） |
| `created_at` | INTEGER NOT NULL | 作成日時 |

```sql
CREATE TABLE user_google_oauth (
  user_id TEXT PRIMARY KEY,
  encrypted_refresh_token BLOB NOT NULL,
  primary_calendar_email TEXT,
  primary_calendar_id TEXT,
  last_sync_at INTEGER,
  created_at INTEGER NOT NULL,
  invalidated_at INTEGER,       -- R-072: リフレッシュ失敗（invalid_grant等）を検知した時刻。NULL=正常
  last_error TEXT                -- R-072: 直近のリフレッシュ失敗理由（診断用の生メッセージ）
);
```

**制約・運用:**
- 連携解除時は行ごと削除（`DELETE /api/google/oauth`）
- 暗号化キーは `.env` の `GOOGLE_OAUTH_ENCRYPTION_KEY`（Phase 2 着手時に保管場所を最終確定）
- アクセストークンは保管しない（リフレッシュトークンから都度発行し、メモリ内のみで使用）
- **R-072: `invalidated_at`/`last_error`（マイグレーション追加カラム）**: `refreshAccessToken()`が`invalid_grant`を検知したら`invalidated_at`に現在時刻・`last_error`にエラーメッセージを記録する。`invalidated_at`がNULLでない間は自動同期を試行せず、設定画面に再連携を促すUIを表示する（詳細: `03_画面設計.md` §12.1、`06_変更履歴.md` R-072）
- **既知の運用上の根本原因**: OAuth同意画面が「テスト中（Testing）」ステータスのままだと、リフレッシュトークンは発行から7日で強制失効する。Google Cloud Consoleで「本番公開」へ切り替えることを推奨（この設定変更はGoogleアカウントを持つ発注者本人のみが行える。コード側の対応では解決しない）

### 3.7 external_events_cache テーブル（R-034 Phase 2）

Google カレンダーから取得したイベントのキャッシュ。TTL 15 分でリフレッシュ。

| カラム | 型 | 説明 |
|:--|:--|:--|
| `id` | TEXT PK | `"google:{event_id}"` 形式の合成キー |
| `user_id` | TEXT NOT NULL | users.user_id への外部キー（CASCADE DELETE） |
| `calendar_id` | TEXT NOT NULL | カレンダー ID（primary は primary_calendar_id と同値） |
| `event_id` | TEXT NOT NULL | Google 側の event id |
| `start_at` | INTEGER NOT NULL | 開始時刻（Unix epoch sec） |
| `end_at` | INTEGER NOT NULL | 終了時刻（Unix epoch sec） |
| `all_day` | INTEGER NOT NULL DEFAULT 0 | 終日フラグ（1=終日） |
| `title` | TEXT | イベントタイトル（**方針変更により保存 OK**。Youkan は晴樹さん専用） |
| `location` | TEXT | 場所（任意。詳細モーダルで表示） |
| `fetched_at` | INTEGER NOT NULL | このキャッシュ行を取得した時刻 |

```sql
CREATE TABLE external_events_cache (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  calendar_id TEXT NOT NULL,
  event_id TEXT NOT NULL,
  start_at INTEGER NOT NULL,
  end_at INTEGER NOT NULL,
  all_day INTEGER NOT NULL DEFAULT 0,
  title TEXT,
  location TEXT,
  fetched_at INTEGER NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE
);
CREATE INDEX idx_external_events_user_date ON external_events_cache(user_id, start_at);
```

**運用:**
- TTL: `fetched_at` から 15 分経過したら次回 `GET /api/calendar/grid` で再取得
- 手動更新（`POST /api/google/calendar/refresh`）は 60 秒クールダウン
- 連携解除時は `user_id` 一致行を全削除（FK の CASCADE で自動）
- Phase 3 で `calendar_id` ごとのテナント割当を追加（別テーブル `user_calendar_assignment` 予定）

### 3.8 assigned_to の値域整理（ID空間、R-050 Phase1）

`items.assigned_to` は単一カラムに2種類のID空間が混在している。discriminator列を追加するスキーマ変更は行わず、**アプリケーション層の解決ロジックで判別する**方針とする（2026-07-09 kaigi2会議で決定。詳細: `docs/kaigi/2026-07-09-R050テナント型AI中枢設計.md`）。

| 値の形式 | 参照先テーブル | 判定方法 |
|:--|:--|:--|
| `u_` プレフィックス付き文字列 | `users.id` | 文字列先頭が `u_` |
| プレフィックスなしの整数（文字列） | `assignees.id` | 上記に一致しない場合のフォールバック |
| どちらにも一致しない値（孤児データ） | なし | 自動修復しない。「未割当」表示＋ログ出力 |

- 実データ検証（2026-07-09時点）で、会社アイテム（`tenant_id` あり・`assigned_to` 非NULL）60件中58件（97%）が `u_` 形式であることを確認済み。既存の `LEFT JOIN assignees a ON items.assigned_to = a.id` はこの97%で担当者名を`NULL`にする表示バグを持つ。
- 解決方法: `backend/ItemController.php::getAssigneeEmail()` に既に実装済みの `u_` プレフィックス判定パターンを、一覧系クエリ（`TodayController.php` / `ItemController.php` の担当者名解決ロジック）へ横展開する。新規マイグレーションスクリプトは不要。
- 孤児データ（例: `u_697b2bfb28bee`）は自動修復・削除をせず、「未割当」表示とアプリケーションログ出力で可視化する。実数の棚卸し（`SELECT assigned_to, COUNT(*) FROM items WHERE tenant_id IS NOT NULL GROUP BY assigned_to` 相当）はPhase1実装時またはPhase2着手前に別途行う。

**担当候補の型（discriminator語彙）:**

フロント/バックエンドで担当候補の由来（`users` 由来 / `assignees` 由来）を区別する型を以下の名称で確定する。Phase3（AI提案設計）以降でこの語彙を再定義しない。

```ts
type AssigneeKind = 'user' | 'assignee';
```

- `'user'`: `assigned_to` が `u_` プレフィックス形式（`users.id` を参照）
- `'assignee'`: `assigned_to` が整数ID形式（`assignees.id` を参照）

### 3.9 改善要望送信フォームの永続化（ファイルベース、R-071）

DBテーブルは追加しない。送信内容はサーバーローカルのファイルシステムに直接保存する（`docs/requests.md`/`requests_log.md` と同様、Markdownを正本とする設計を踏襲）。

**保存先パス（バックエンド実行ディレクトリからの相対パス）:**

| 種別 | パス |
|:--|:--|
| 要望本文の追記先 | `backend/data/requests_sub.md` |
| 添付画像 | `backend/data/requests_sub_uploads/{uuid}.{ext}` |

`backend/data/` は既存の `backend/` ディレクトリ直下だが、`.gitignore` でGit管理外にする（ローカル開発機とサーバーで別々の内容を持つ、環境固有データという扱い）。

**エントリのフォーマット（`requests_sub.md`への追記例）:**

```markdown
## 2026-07-29 14:32 (user: fjt.suntree@gmail.com)

カレンダーのここが使いづらい。スクショ添付。

![screenshot](requests_sub_uploads/3f9a2b1c.png)

---
```

**重要な運用制約（デプロイとの整合性）:**

`backend/data/` は `.env`・`*.sqlite`・`*.log` と同じ「本番のみに存在し続けるべきデータ」であるため、`upload.ps1` の `Copy-Item -Path $backendDir -Exclude` リストに `data` を追加しなければならない。追加を怠ると、次回デプロイ時にローカル（空 or 開発用）の内容で本番の `backend/data/` が上書きされ、蓄積された要望・画像が消失する。実装時は必ずこの一点を確認すること。

**回収（同期）はAPIを持たない手動運用:**

- 発注者または指揮AIが、既存の `upload.ps1` と同じSSH鍵・接続先設定を使い、不定期に `scp` （または類似の小さな回収用スクリプト）で `backend/data/requests_sub.md` と `backend/data/requests_sub_uploads/` をローカルのgitリポジトリ配下（`docs/requests_sub.md` / `docs/requests_sub_uploads/`）へダウンロードする
- ダウンロードしたファイルは通常のファイルとしてgit管理下に置いてよい（回収した時点のスナップショットをコミットする運用）
- 回収後、内容を読んで良いと判断した項目は人力で `docs/requests.md` に書き写す

## 4. アイテム状態定義（State Matrix）

### 4.1 基本ステータス（JudgmentStatus）

「進捗」ではなく**「判断（今考えるか・否か）」**で分類する。

| ステータス | 日本語 | 意味 | 表示場所 |
|:--|:--|:--|:--|
| `inbox` | 受信箱 | 未判断。判断待ち | Inbox（左カラム） |
| `focus` | 今日やる | 「今日意識と時間を向ける」と判断した状態 | Stream（中央カラム） |
| `waiting` | 待機中 | 他者待ち、または開始日待ち | Waiting（左カラム） |
| `pending` | 保留 | 「今はやらない」と意図的に判断した状態 | Pending（左カラム） |
| `someday` | いつかやる | 自分で寝かせると決めた状態。期限なし・キャパ計算除外（R-028） | パノラマの専用バケット |
| `done` | 完了 | 作業が終了した状態 | Log / Archive |
| `cancelled` | 断った | 「断る」判断の結果（R-124）。`done`とは区別し、全体一覧・パノラマの「履歴」に完了と並んで表示され続ける | Log / 履歴 |

> **R-124補足**: `cancelled`導入前は画面ごとに`done`（状況把握/全体一覧経由）または`decision_rejected`というJudgmentStatus型の外側のレガシー値（フロー/カレンダー経由）を書き込む2系統が併存し、「保留」を「断る」に取り違える・「断る」が「完了」扱いになる等のバグの温床になっていた。`decision_rejected`は移行済みデータの表示互換のためフィルタ・シェルフ分類上は`cancelled`と同じ扱いを継続するが、新規の書き込みは行わない。

### 4.2 フラグとの組み合わせ

#### Inbox フェーズ

| ステータス | 組み合わせ | 意味 |
|:--|:--|:--|
| `inbox` | 標準 | 純粋な未処理アイテム |
| `inbox` | `interrupt: true` | 割り込み/緊急。Inbox最上部に強調表示 |

#### Focus フェーズ

| ステータス | 組み合わせ | 意味 |
|:--|:--|:--|
| `focus` | 標準 | 今日のタスクキュー |
| `focus` | `isEngaged: true` | 現在実行中（Active Focus）。FocusCardとして中央で最大化 |
| `focus` | `is_executing: true` | 実行中フラグ（Backend永続化）。isEngagedと同義 |
| `focus` | `isProject: true` | プロジェクト全体のFocus |

#### Waiting フェーズ

| ステータス | 組み合わせ | 意味 |
|:--|:--|:--|
| `waiting` | 標準 | 他者待ち（Delegated） |
| `waiting` | `prep_date`が未来 | 開始日待ち（Scheduled）。カレンダーに表示 |
| `waiting` | `prep_date`が過去/今日 | 開始可能（Ready）。Inbox/Focusへ移動候補 |

#### Pending フェーズ

| ステータス | 組み合わせ | 意味 |
|:--|:--|:--|
| `pending` | 標準 | いつかやる（Someday） |
| `pending` | `due_date`が未来 | 期限付き保留 |

| フラグ | 値 | 意味 |
|:--|:--|:--|
| `isProject` | true | プロジェクト化。子タスクを持てる |
| `projectId` | ID | 特定プロジェクトの子タスク |

### 4.4 ライフサイクル（状態遷移）

```
inbox → focus      （今日やる）
inbox → waiting    （人に頼む / 開始日待ち）
inbox → pending    （今はやらない）
inbox → done       （もう終わった）

focus → done       （完了）
focus → inbox      （やっぱり保留解除）
focus → waiting    （待ちに変更）
focus → pending    （やっぱり保留）

waiting → inbox    （待ち解除）
waiting → focus    （待ち解除して即実行）
waiting → done     （待っている間に解決）

pending → inbox    （再検討）

inbox/focus/waiting/pending → cancelled  （「断る」判断。R-124）
```

### 4.4.1 「断る」（Decision: No）の解決ロジック（R-124）

判断UI（yes/hold/no）における「断る」操作は、`JWCADTategu.Web/src/features/core/youkan/logic/decisionResolution.ts`の`decisionToStatus(decision, note)`に一本化されている。

| decision | note | 結果status |
|:--|:--|:--|
| `yes` | — | `focus` |
| `hold` | — | `pending` |
| `no` | `someday` / `intent` | `pending`（保留棚への退避。例外ルート） |
| `no` | それ以外（通常の「断る」） | `cancelled` |

この関数は以下の画面すべてから呼び出される（バックエンド`DecisionController.php::resolve()`も同じ対応表で`cancelled`を書き込む）。

- 状況把握（PanoramaBoard）・登録と集中（DashboardScreen）: `useYoukanViewModel.resolveDecision`経由
- フローチャート（FlowScreen）・ガント右クリックメニュー（RyokanGanttView）: `decisionToStatus`を直接呼ぶか、`ApiClient.resolveDecision`（バックエンド`DecisionController.php`）を経由
- カレンダー（VolumeCalendarScreen）: `ApiClient.resolveDecision`を経由

R-124以前は画面ごとに「断る」の結果statusが別々に実装されており（`done`書き込み・`decision_rejected`書き込み・直接`done`上書きの3系統）、「保留」を「断る」に取り違える、「断る」が「完了」扱いになる等のバグが起きていた。

**UI文言（発注者承認済み）**: 「キャンセル」だけの婉曲表現を避け、「断った」という判断行為を必ず表示に残す。`logic/statusUtils.ts`の`STATUS_META.cancelled`に`label`（狭い箇所用）と`labelWide`（広い箇所用）の2種を定義する。

| 箇所の例 | 文言 |
|:--|:--|
| フローノードのバッジ、全体一覧の狭い行など省スペースな箇所 | 「断った」（`STATUS_META.cancelled.label`） |
| 右クリックメニュー、ステータス選択UI、確認ダイアログなど表示幅に余裕がある箇所 | 「キャンセル・断った」（`STATUS_META.cancelled.labelWide`） |

### 4.5 due_status（納期確定状態、R-073で明文化）

`items.due_status`（`TEXT NULL`、ENUM制約なし）は`due_date`とは独立した「納期の確からしさ」を表すフラグ。旧設計書（`docs/99_Archive/Reference_Log/202601122223再定義/納期_入力表示活用_設計完全版.md`）で定義されていたが、現行仕様書に値域・遷移条件が未記載だったため本改訂で明文化する。

| 値 | 意味 |
|:--|:--|
| `null` | 未設定（デフォルト） |
| `confirmed` | 納期確定（発注者が実際に日付を入力・変更した） |
| `waiting_external` | 相手都合で未確定（先方回答待ち等） |

フロント型定義（`types.ts`）には表示用の追加値（`today`/`future`/`overdue`/`someday`）も同じユニオン型に含まれるが、これらは`due_date`から計算される表示ラベルであり、DBに保存される状態は`null`/`confirmed`/`waiting_external`の3値のみ。

**遷移条件（重要）**: `dueStatus`の更新は、`due_date`が**実際に入力・変更・クリアされた時のみ**行う。日付欄へのフォーカス／ブラーなど、値が変化しない操作では絶対に更新してはならない（R-073: `SmartDateInput`の差分チェック漏れにより、値が変わらないブラーでも`onChange`が発火し`dueStatus: 'confirmed'`が意図せず送信されるバグが発生していた）。

### 5.2 認証

Youkan は2系統の認証を**併存**させる（R-096）。`BaseController::authenticate()` が共有セッションを先に試し、成立しなければ従来のJWT認証へフォールバックする。auth-hub への移行は既存方式の「置き換え」ではなく「選択肢の追加」であり、既存の挙動は変更しない。

**(a) auth-hub 共有セッション（R-096 で追加）**

- Cookie: `df_session`（`path=/`。ドメイン全体で共有。リソース隔離ルールの唯一の例外）
- 検証: `backend/auth_client.php` の `currentUser()` が auth-hub の `POST /contents/auth/auth/verify` へ問い合わせる
- auth-hub が返すのは `{id, name}` のみ。そこから `users.auth_user_id` で Youkan のユーザー行に解決する
- 以下のいずれかに当たる場合は認証成立とせず、(b) へフォールバックする: Cookieが無い／auth-hub が無効と判定した／`auth_user_id` が一致する Youkan ユーザーが存在しない
- ベースURLは環境変数 `AUTH_HUB_BASE` で上書きできる（既定は本番の `https://door-fujita.com/contents/auth`）
- 仕様の正本: `C:\Fujiruki\Projects\auth-hub\docs\SPEC\01_認証仕様.md`

**(b) 独自JWT（従来方式・継続）**

- JWT Bearer Token認証
- リクエストヘッダー: `Authorization: Bearer <token>`
- クエリパラメータ: `?token=<token>`（フォールバック）
- 会社アカウントログイン（`/auth/login/tenant`）と自己サインアップ（`/auth/register`）はこの系統でのみ提供する。auth-hub は「人」しか認証しないため、テナント自体としてのログインは共有セッションでは表現できない

**テナント文脈の所在**

auth-hub が担うのは「誰であるか」だけで、マルチテナント（テナント切替）は Youkan 側に残す（auth-hub 仕様書 §8-A）。`tenants` / `memberships` テーブルと `/auth/switch-tenant` は従来通り Youkan が管理する。

**既存ユーザーの auth-hub への移行**

`backend/scripts/migrate_users_to_auth_hub.php`（既定はドライラン、`--apply` で書き込み）。パスワードハッシュは PHP 標準 `password_hash()` の出力で文字列自体にアルゴリズムが埋め込まれており、auth-hub 側の検証も `password_verify()` のため、bcrypt のハッシュをそのまま移設すれば既存パスワードで引き続きログインできる（作り直し・リセット不要）。Youkan の `users.password_hash` は (b) が併存する限り削除しない。

### 5.3 アクセス制御

アイテムの可視性ルール:
1. **個人タスク**（tenant_id IS NULL）: created_by = 自分 OR assigned_to = 自分
2. **会社タスク**: 所属テナントのアイテム AND（created_by = 自分 OR assigned_to = 自分）
3. **プロジェクトフォーカスモード**: 上記に加え、focusしたプロジェクトとその子孫のアイテムも表示
4. **管理者スコープ**（R-050 Phase1・新設）: 所属テナントで `memberships.role IN ('owner', 'admin')` のユーザーは、そのテナント内であれば `assigned_to` を問わずアイテムを閲覧できる。既存の1〜3は変更しない（デフォルト表示は従来通り「自分が創建者 or 自分が担当者」のみ）。管理者が他者の担当分を見る場合は、一覧系エンドポイント（`/items`・`/today` 等）に明示的なクエリパラメータ（例: `assigned_to=<id>&scope=team`。パラメータ名は実装Agent確定）を指定した場合にのみ発動する。新しいロールモデルは作らず、既存の `memberships.role` 列を使う。用途は画面2「担当者別ビュー」（詳細: `docs/kaigi/2026-07-09-R050テナント型AI中枢設計.md`）。

  **実装上の注意（既存コードの不整合）**: `ItemController.php` の `isAdmin` 判定（`update()`/`archive()` 等）は現状 `role === 'admin'` のみを見ており `owner` を含まない。一方 `TenantController.php` は `role !== 'owner' && role !== 'admin'` で両方を管理者として扱っている。管理者スコープの実装時は `TenantController.php` 側のパターン（owner/admin両方を管理者とみなす）に合わせること。

## 補足: 状態・Today・プロジェクト文脈の直交性（2026-07-07）

`items.status = 'focus'` は永続化される状態値であり、Today キューへの所属そのものではない。Today キューは `todayCandidates` / `todayCommits` / `executionItem` として取得・構成される実行文脈である。

`focusedProjectId` / `activeProject` は、データ取得・表示・新規追加時の `project_id` 継承・量感計算の絞り込みに使うプロジェクト文脈である。`status = 'focus'` とは別概念であり、名称上の「focus」に引きずられて同一視してはならない。
