## 1. R-0167 全体一覧「＋」追加時の404

- 症状: 全体一覧のプロジェクト右の「＋」でアイテムを追加すると、`Creating item` の後に別アイテム（`019f3bed-…`）への `Updating item` が走り、`backend/index.php/items/019fea80-…` が404（`Item not found or access denied`）。以降のアイテム作成は続行できている
- 原因未確定。実装Agentは根本原因を調査（追加処理の呼び出し経路、更新対象IDの由来、そのIDが本番に存在しない/テナント違い/削除済みの可能性）。本番DBは**読み取り専用**でのみ調査可。対症療法（例外の握りつぶし）は禁止
- **根因（確定）**: 404の対象 `019fea80-…` は新規作成アイテムではなく、同プロジェクト配下の**ゴミ箱内（`deleted_at` 設定済み）の子アイテム**（本番DBをSELECTで確認）。直前の `Updating item 019f3bed-…`（親プロジェクト）のレスポンス `affectedDescendantIds`（`getAllDescendantIds` は削除済みも含む）を `useYoukanViewModel.refreshItems` が `ApiClient.fetchItemsByIds` で再取得し、`GET /items/{id}`（`show()` は `deleted_at IS NULL` 限定）が404となる。`fetchItemsByIds` は失敗を `catch(() => null)` で許容する設計だが、`request` が非silentのため全体エラートーストが出ていた。加えて `request` のGET重複排除で `fresh.finally(...)` の派生Promiseが未処理拒否（`Uncaught (in promise)`）になっていた
- **修正**: `fetchItemsByIds` を silent（404はスキップ、トースト無し）にし、GET重複排除の派生Promiseの未処理拒否を吸収（呼び出し元への拒否伝播は不変）。テスト `api/__tests__/client.fetchItemsByIds.test.ts`
- 修正後も、エラー文言はユーザーに分かる日本語で表示されること（既存の共通エラー表示に従う）
- 受け入れ条件: 「＋」で追加しても404が出ない。追加したアイテムが期待どおり親プロジェクト配下に作られる

## 2. R-0168 ガント月移動

調査結果（静的追跡）。対象画面は `VolumeCalendarScreen`（`RyokanCalendar`/`RyokanGanttView`/`CalendarHeader`）。
- A（確度高）: 表示列は今月±2ヶ月のみ。矢印で範囲外の月へ出ると、`RyokanCalendar.tsx` の pendingScrollTarget 消費が範囲拡張後・`allDays` 更新前に走り、スクロールが空振りして列だけ入れ替わる。ラベルも誤った月に書き換わる
- B（確度中〜高）: `RyokanGanttView.tsx:475-478` のラベル月判定が左固定列256pxを考慮せず、中央日付が約11〜16日後ろにずれる。月後半で翌月ラベルになり、次の「次月」で1ヶ月飛び越す。`scrollToDate`（:455-472）も同様
- C（確度中）: クリック直後のcurrentDate更新・pendingScrollTarget・250msデバウンスの `handleVisibleMonthChange` が競合
- D（確度低）: 「今月を表示」も範囲外で空振りしうる。Bによる誤ラベルで `isCurrentMonth` により押せなくなる

- A: pendingScrollTargetの消費を「対象日の `data-gantt-date` 要素がDOMに存在する」ことを条件にする。range拡張とスクロールを一本化し、focusDate由来のrange再生成との二重管理を解消。初期スクロールも「対象要素が実在したときのみ完了扱い」
- B: ラベル算出で固定列256pxを補正（または `data-gantt-date` 要素の実位置から中央日を求める）。`scrollToDate` も同様
- C: 矢印クリック起点のプログラムスクロール中は `handleVisibleMonthChange` の反映を抑止する
- D: A・Bの修正後に「今月を表示」が範囲外でも動くことを確認
- グリッド/タイムライン表示は別実装。共通の `scrollToDateElement` を変える場合は回帰を確認

受け入れ条件: 今月から次月・前月を6回ずつ押して、毎回1ヶ月ずつ進み、押すたびに該当月が画面中央に表示され、ラベルとスクロール位置が一致する。「今月を表示」で範囲外からも戻れる。速い連打でも最終的に矢印で指定した月に収束する。
テスト（Red先行）: ①範囲外月への `scrollToMonth` でscrollToがleft>0で呼ばれる ②ラベル算出（colWidth 16/24、固定列256px込み） ③次月4回でSep→Oct→Nov→Dec→Jan

### 2.1 再調査（2026-09-25 実測後）— 根本原因と修正

初回修正（A〜D）のデプロイ後も「1・2クリック目は表示位置がほぼ動かず、3クリック目に約3ヶ月ジャンプ」が残った。前面ブラウザでの実測（マンスリー・列幅24: 1クリックの scrollLeft 変化が +11px / +2px / −13px＋allDays 先頭+91日、列幅・スケールを変えても3クリック周期。ヘッダーと本体の同一日付セルの左端差は常に0）をもとに原因を特定した。

**根本原因1（主因）: ヘッダー↔本体の scrollLeft 同期が本体の smooth スクロールを打ち切る** — `RyokanGanttView.tsx` の同期処理（旧 :408-440）は `isSyncing` フラグを rAF で解除していた。本体を `scrollTo({behavior:'smooth'})` すると、フレーム毎に本体の scroll イベント→`header.scrollLeft = body.scrollLeft`→rAF でフラグ解除、の順に進む。ヘッダーへの代入で発生するヘッダー側の scroll イベントは**次フレーム**に届くため、そのときフラグは既に解除されており `body.scrollLeft = header.scrollLeft`（1フレーム前の古い値）が実行され、smooth スクロールがキャンセルされて本体が1フレーム前の位置へ戻る。結果として1クリックあたり1フレーム分（+2〜11px）しか動かない。ラベル（currentDate）だけは矢印で先に更新されるため「ラベル10月・中央9/25」のずれが生じる。ヘッダーと本体の差が常に0なのはこの書き戻しが両者を揃えるため。

**根本原因2: 3クリック目の range 張り直しで focusDate（25日）へ瞬間移動** — 矢印は `currentDate` を +1ヶ月するが初期値は `new Date()`（例: 9/25）で日付を保持していた。3回目で currentDate=12/25 が表示範囲（今月±2ヶ月、6/28〜12/5）を出ると `RyokanCalendar.tsx` の range 効果（:331-381）が anchor=12/25 で range を張り直し `hasInitialScrolled=false` にし、初期スクロール効果（:409-417）が `focusDate`（12/25）へ**瞬間**スクロールしていた。これが「約3ヶ月ジャンプ」の実体（本来の目標 12/15 への smooth スクロールは原因1で打ち切られる）。

**根本原因3: 同期連打で1クリックしか反映されない** — `VolumeCalendarScreen.tsx` の矢印ハンドラがクリック時点の `currentDate`（render クロージャ）から翌月を計算し `handleNextMonth`（同じくクロージャ依存）を呼んでいたため、同一ティック内の連打は全て同じ月を指し、8連打が1ヶ月分にしかならなかった。

**修正**:
1. `RyokanGanttView.tsx` 同期: rAF フラグを廃止し、相手へ書き込んだ値（読み戻した値）を記憶して「その値と一致する自分の scroll イベント（echo）」だけを無視する。ユーザーがヘッダーを直接スクロールした場合は従来どおり本体へ同期し、直前の同期値へ戻す操作も反映される。
2. `VolumeCalendarScreen.tsx`: 矢印は `setCurrentDate(prev => prev±1ヶ月の1日)` の関数型更新のみ行い、コミット後の effect（`monthNavRequestedRef` で矢印起点のときだけ）で確定した `currentDate` の月へ `scrollToMonth` を1回呼ぶ。目標日は「確定した currentDate の月の15日」に一元化。`useVolumeCalendarViewModel` の `handleNextMonth/handlePrevMonth`（クロージャ依存）は削除。
3. `RyokanCalendar.tsx` 初期スクロール: `pendingScrollTarget` があればそれを初期位置にし（focusDate より優先）、成功時に消費する。range 張り直し時も目標日は1つ（月中央）で、瞬間移動→戻りの二段階にならない。

矢印の基準は引き続き `currentDate`（＝ラベルの月。スクロール由来の表示月通知で同期され、プログラムスクロール中1000msは通知を抑止）とし、「スクロール位置の中央月」を別途参照する設計にはしなかった（原因1の修正で smooth スクロールが完走するため、抑止解除後の中央月と currentDate は一致する）。

テスト（Red→Green）: `RyokanGanttView.headerSync.test.tsx`（echo 書き戻しで本体が戻らない／ユーザーのヘッダー操作は同期される）、`RyokanCalendar.ganttMonthNavRange.test.tsx`（range 張り直しを伴う次月で 15日以外へ scrollTo しない）、`VolumeCalendarScreen.monthNav.test.tsx`（同一ティック8連打で+8ヶ月・最終月へ1回 scrollToMonth、前後交互連打の収束）。

範囲外（提案のみ）: 表示範囲が今月±2ヶ月のウィンドウのため、矢印3回ごとに約5.1万要素の DOM を丸ごと再生成する。重さ自体の対策（範囲の縮小・列の仮想化・range を張り直さず伸長する）は別要望とする。

## 3. R-0169 ガントの非表示タスク
