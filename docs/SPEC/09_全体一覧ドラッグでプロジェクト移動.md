# 09. 全体一覧ドラッグでプロジェクト移動

- 要望: R-155（`docs/requests_log.md`）
- 原文・機能要件: `docs/reference/vision/2026-08-28_全体一覧ドラッグでプロジェクト移動.md`（全文が正）
- 前提: Y1（`docs/SPEC/07_Beaver連携.md`）・Y2（`docs/SPEC/08_Beaver連携Y2.md`）は無変更。本書はその上に積む追加仕様であり、Y1/Y2の不変条件・階層解決規則・API契約をすべて継承する
- 対象画面: 全体一覧（`OverviewBoard.tsx` / `OverviewItem.tsx`、Newspaper View）

## 1. 目的

全体一覧画面上で、タスクをドラッグして任意のプロジェクト（入れ子のサブプロジェクト・Beaver work_package含む）へドロップし、所属階層（`project_id` / `parent_id`）を変更できるようにする。詳細な背景・UX要件は原文文書を正とする。

## 2. 不変条件

1. 階層解釈（`project_id` / `parent_id` の意味、`children(N)` 解決規則）は `hierarchy.ts` の既存ロジック（`buildHierarchicalList` / `collectDescendantIds` / `normalizeId`）をそのまま再利用する。ドラッグ機能専用の親子解釈を新設しない
2. Beaver由来の `external_project_links` / `external_work_package_links`、`baseline_minutes` 等のexternalリンク情報は、所属変更によって一切書き換えない（更新対象は `items.project_id` / `items.parent_id` のみ）
3. 移動操作は所属階層のみを変更する。title・status・due_date・prep_date・estimated_minutes・assigned_to・dependencies・meta・作成者情報など、所属と無関係なフィールドは変更しない
4. Y2の再帰負荷モデル（`effective_total = max(baseline, Σchildren)`、`BeaverCapacityService::buildChildrenOf()` の parent_id優先・project_idフォールバック規則）を壊さない。移動前後で対象タスクの `estimated_minutes` が二重計上されたり負荷から消えたりしない
5. ドラッグ専用のDB直接更新経路を作らない。既存の `PUT/PATCH /items/:id`（`ItemController::update()` → `updateEntity()`）を使う
6. 名前による自動統合・自動判定はしない。移動先は常にユーザーのドラッグ操作で明示的に決まる

## 3. スコープ

原文文書 §6・§7・§17 のとおり。

**初版に含む（優先順位順）:**
1. 通常タスク → ルートプロジェクトへの移動
2. 通常タスク → サブプロジェクト／Beaver work_packageへの移動
3. 移動直後のUndo（トースト＋「元に戻す」）

**初版に含まない（スコープ外）:**
- プロジェクト／サブプロジェクト自体のドラッグ移動（原文§7。既存ロジックを流用して安全に対応できると判明した場合のみ着手可、無理に含めない）
- 名前による重複案件自動検出・自動統合
- 旧プロジェクトの自動削除／自動アーカイブ
- 複数タスクの一括選択ドラッグ
- プロジェクト間の自動工数調整・Beaverへの逆同期
- Y3全般（バッファ・担当別simulation・自動仮配置）

## 4. DnD実装方式

既存導入済みの `@dnd-kit/core`（`PanoramaBoard.tsx` の実装パターンを踏襲）を使う。新規ライブラリを追加しない。

- `DndContext` + `PointerSensor`（`activationConstraint: { distance: 8 }`）+ `KeyboardSensor` + `pointerWithin` collision detection + `DragOverlay`
- ドラッグ可能: `type: 'item'` の行（通常タスク）のみ。`type: 'header'`（プロジェクト行）はドラッグ不可（§3のスコープによる）
- ドロップ可能: `type: 'header'` の行（`buildHierarchicalList` が生成する全てのプロジェクト／サブプロジェクト／work_package header）。1 header = 1 `useDroppable` ターゲットとし、`id` は既存の `header-${projectId}` 形式をそのまま使う
- `OverviewBoard.tsx` の CSS `columnCount` による段組みレイアウトはそのまま維持する（`pointerWithin` は画面上の絶対座標で判定するため、複数カラムでも動作する）
- タッチ操作: `PointerSensor` はマウス・タッチ両対応のため、長押し等の追加実装なしで初版のタッチ対応を満たす

## 5. ドロップ判定・ハイライト

- ドラッグ中、`over` が有効な header と一致する時のみ、その header 行だけをハイライトする（背景強調＋枠線＋「○○へ移動」ラベル。原文§3.1・§11準拠）
- 親子のheaderは別IDのため、`over.id` の一致判定だけで自然に「現在の実ドロップ先だけ」が光る（親子同時ハイライトは発生しない。原文§3.2）
- **ドロップ不可として無効化する対象**（`useDroppable` の `disabled` で制御し、無効時はハイライトも禁止カーソルも出す）:
  - ドラッグ中タスク自身の祖先チェーンの一番下（自明に無意味な移動: 現在の直接の親への再ドロップは許容してよいが、実装は無害なので許容側で良い）
  - ドラッグ中タスクの子孫（循環防止）: `collectDescendantIds(allItems, draggedItemId)` の結果に含まれる `projectId` の header
  - ドラッグ中タスクとテナントが異なる header（`item.tenantId` と `header.project.tenantId` が不一致。個人アイテム↔他テナントも含む）
  - `isArchived` の header（`buildHierarchicalList` は archived を除外表示するため、通常は一覧に出てこず自然に対象外になる。念のため防御的にチェックする）

## 6. 所属変更の値の決め方

**既存の `hierarchy.ts` 解決規則（parent_id優先、無ければproject_idへフォールバック）に合わせて決定する。ドラッグ専用の値の推測をしない。**

- **ルートプロジェクトへドロップ**（原文§4.1）:
  `updateItem(taskId, { projectId: targetHeaderProjectId, parentId: null })`
- **サブプロジェクト／Beaver work_packageへドロップ**（原文§4.2）:
  `updateItem(taskId, { parentId: targetHeaderProjectId, projectId: rootProjectIdOf(targetHeaderProjectId) })`
  - `rootProjectIdOf()` は、ドロップ先ノードから `parentId` を辿って（無ければ `projectId` へフォールバックして）ルート（`parentId` も `projectId` も持たない、またはBeaver案件トップである）まで遡る新規ヘルパーとして `hierarchy.ts` に追加する。既存の `buildHierarchicalList` の親子解決条件式と完全に同じ優先順位を使うこと（実装Agentが1箇所の判定ロジックとして共通化してよいが、別解釈を作らないこと）
  - Y2のwork_packageは既に `project_id = 案件ルートID` を持つ（`docs/SPEC/08_Beaver連携Y2.md` §3）ため、work_packageへのドロップでは `rootProjectIdOf` は単に対象work_packageの `projectId` を返せばよい（探索不要）
- `updateItem` は差分更新（`Partial<Item>`）のため、上記2フィールド以外は送信しない。これにより不変条件3（他フィールド非破壊）を自然に満たす

## 7. バックエンド: 新規追加が必要な検証（`backend/ItemController.php::update()`）

現状調査済みの事実: `update()` は `projectId` 変更時のテナント越境チェック・担当自動同期・`cascadeTenantToDescendants` を持つが、**`parentId` 変更単体の循環参照チェックは存在しない**。今回新規に追加する。

- `parentId` が変更される場合（`array_key_exists('parentId', $data) && $data['parentId'] !== $existing['parent_id']`）:
  1. 新しい `parentId` が自分自身のIDと一致 → `400 Bad Request`（"Cannot move item into itself" 等）
  2. 新しい `parentId` が自分の子孫（`parent_id`/`project_id` の再帰、既存の `getAllDescendantIds()` 相当のロジックを流用）に含まれる → `400 Bad Request`（"Cannot move item into its own descendant"）
- `projectId` 変更時の既存テナント越境チェック（837-869行目付近）は流用したまま使う。`parentId` のみ変更で `projectId` が変わらないケース（同一ルート案件内でのサブプロジェクト間移動）ではテナント越境は原理上発生しないため、追加チェックは不要
- 上記エラー時のレスポンス形式は既存の `sendError()` パターンに合わせ、フロントは同じ形式でエラーメッセージをトーストに表示する

## 8. フロントエンドの保存フロー

原文§14の2案のうち「保存成功後にUI移動」方式を採用する（既存 `PanoramaBoard.tsx` の `handleDragEnd` と同じ `await vm.updateItem(...)` → 状態反映パターンに合わせるため。独自の楽観的更新＋ロールバック機構を新設しない）。

1. ドロップ確定 → `await viewModel.updateItem(taskId, { projectId, parentId })`
2. 成功 → ViewModelの状態が更新され、次のレンダーで `buildHierarchicalList` が再計算されて新しい所属位置に表示される
3. 失敗 → 例外をキャッチし、トーストでエラー表示（既存 `useToast` を使用）。UIは何も仮移動していないため、ロールバック処理は不要

## 9. Undo（原文§3.3・優先順位3）

- ドロップ成功後、トーストで「"{taskTitle}"を"{targetProjectTitle}"へ移動しました [元に戻す]」を表示する（既存 `useToast` / `ToastContext` を利用）
- 「元に戻す」クリック時は、移動前の `{ projectId, parentId }` を保持しておき、逆方向に `updateItem` を呼ぶ
- Undoの表示時間は既存Toastのデフォルト設定に従う（新規のタイマー機構を作らない）

## 10. アクセシビリティ代替（原文§13）

ドラッグ＆ドロップ以外の移動手段として、既存の詳細編集モーダル（`DecisionDetailModal` 等）でプロジェクト所属を変更できる経路が現状あるかを実装時に確認し、あれば追加実装不要、なければ既存モーダルへの項目追加を検討する（新規専用UIは作らない）。

## 14. Y3との関係

原文§19のとおり、本機能の実装を理由にY3（バッファ・担当別capacity simulation・仮配置・自動スケジューリング）へ自動的に進まない。完了後は停止し、発注者の判断を待つ。
